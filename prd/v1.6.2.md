# SMC Copilot PRD v1.6.2 Hotfix

## Attachment Runtime Closure & Multi-Run Isolation

**版本**：v1.6.2 Hotfix
**适用仓库**：`loudon84/smc-copilot`
**目标范围**：Desktop Chat → Runtime → Hermes Agent
**优先级**：P0
**版本性质**：架构闭环修复，不新增业务功能

---

# 1. 背景

v1.6 已完成 Chat 主链路向 Runtime 收口，包括：

```text
Desktop
  ↓
Runtime ChatRun / ChatTurn
  ↓
ChatTurnWorker
  ↓
HermesChatExecutor
  ↓
Hermes Gateway
```

并将 Session、Session File、Chat Settings、Workspace 等数据 Ownership 逐步从 Desktop 转移到 Runtime。当前代码中 `ChatTurnWorker` 已经通过 `HermesChatExecutionRequest` 向 `HermesChatExecutor` 传递 `attachment_ids`、`session_id`、`workspace_id` 和上下文。

但附件上传仍存在旧 Desktop 路径：

```text
Renderer
  ↓
aiosFilesAdapter
  ↓
window.chatFiles.uploadDropped
  ↓
Desktop Main
  ↓
hermes-default-chat-attachments
  ↓
~/.hermes/desktop/chat-attachments
```

`aiosFilesAdapter.upload()` 当前仍调用 `window.chatFiles.uploadDropped()`，并未真正进入 Runtime Attachment API。

Desktop Main 又通过 `uploadHermesAttachmentsFromBuffers()` 将文件写入 Desktop 自己的附件目录，并生成 Desktop UUID。

与此同时，发送 Chat Turn 时 `ServeChatRuntimeAdapter` 将这些 Desktop Attachment ID 直接作为 `attachmentIds` 交给 Runtime。

Runtime 执行时却从自己的 `chat_attachments` Repository 查询这些 ID：

```text
Desktop Attachment ID
         ↓
ChatTurn
         ↓
HermesChatExecutor
         ↓
Runtime chat_attachments
         ↓
NOT FOUND
```

`AttachmentService.load_scoped()` 在记录不存在时返回 `ATTACHMENT_NOT_FOUND`，scope 不一致时返回 `ATTACHMENT_SCOPE_MISMATCH`。

由此导致当前附件 Chat 出现：

```text
turn worker failed
```

---

# 2. 当前问题

## 2.1 P0：Attachment Ownership 未真正收口

当前同时存在两套附件系统：

```text
A. Desktop Attachment Store
~/.hermes/desktop/chat-attachments
index.json
Desktop UUID

B. Runtime Attachment Store
chat_attachments
att_xxx
workspace/session/profile scope
```

Chat Upload 使用 A。

Chat Execute 使用 B。

因此：

```text
Attachment Upload SOT ≠ Attachment Execution SOT
```

这是当前故障的直接原因。

---

## 2.2 P0：Runtime 错误被 Worker 覆盖

`HermesChatExecutor.execute()` 在进入 HTTP Stream 的 `try` 之前执行：

```text
resolve instance
ensure gateway
resolve model
load attachments
build attachment context
```

因此附件解析等前置异常可能直接穿透 Executor，最终进入 `ChatTurnWorker` 最外层：

```python
except Exception:
    ...
    turn.error_code = "TURN_FAILED"
    turn.error_message = "turn worker failed"
```

导致真实的：

```text
ATTACHMENT_NOT_FOUND
ATTACHMENT_SCOPE_MISMATCH
WORKSPACE_NOT_FOUND
```

被转换成：

```text
TURN_FAILED
turn worker failed
```

当前 Worker 的兜底行为可直接从源码确认。

---

## 2.3 P0：Abort Run 会影响其他 Run

当前：

```python
def request_abort(run_id):
    cancel_flag_for_run(run_id).set()

    for tid, flag in list(_TURN_CANCEL.items()):
        flag.set()
```

实际上会设置当前 Runtime 进程内所有 Turn 的 Cancel Flag。

因此：

```text
Run A
Run B
Run C
```

如果：

```text
Abort Run A
```

存在误取消 B、C Turn 的风险。

在多 Chat Tab、多 Run、Background Chat 已经存在的情况下，这是 P0 隔离问题。

---

## 2.4 P1：并发控制粒度只到 Run

当前 `ChatTurnScheduler` 实现：

```text
one active turn at a time per Run
```

通过：

```python
repo.list_active_turns(run_id)
```

判断是否可调度。

因此：

```text
Run A → Hermes Session S1
Run B → Hermes Session S1
```

仍可同时运行。

而 Hermes WebUI 的原生执行模式明确采用：

```text
_get_session_agent_lock(session_id)
```

保证同一个 Hermes Session 不并发执行。

SMC Runtime 应保持相同的 Session 级执行不变式。

v1.6.2 只完成以下四项。

```text
P0-1 Attachment Runtime Closure
P0-2 Error Transparency
P0-3 Run-scoped Cancellation
P0-4 Hermes Session Execution Isolation
```

最终形成：

```text
Desktop
   │
   │ UI / local file picking
   ▼

   │
   ├── Attachment Ownership
   ├── Session Ownership
   ├── Workspace Ownership
```

Hermes Agent 本身继续作为 Agent 编排运行时；工具执行、Session、Agent Loop 等能力留在 Hermes，不将附件元数据治理重新放入 Hermes。

```text

```


**v1.6.2 的核心判定线只有一句：**

> **进入 Serve Chat 之后，附件、会话、Turn、Queue、错误和并发控制全部由 Runtime 管理；Desktop 只负责文件选择与 UI，Hermes 只负责 Agent 执行。**

这能直接修复当前 `BaiduSearch.zip → turn worker failed`，同时消除多 Chat / 多 Run 场景下已经暴露出来的附件双 SOT、跨 Run Cancel 和同 Hermes Session 并发三个结构性问题。
