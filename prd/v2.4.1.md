## 1. 版本决策

下一版本定义为 **v2.4.1**，不进入 v2.5。

原因：v2.4 已完成持久化、Job Worker、Ring 0 API、Observer、Handover Extension 与 Evidence 模板，但真实 Ring 0 仍为 `NO-GO`。当前批次可在未校验 Job、Target、Gateway、Work Probe 与 SLO 的情况下推进并完成；现有证据目录仅包含模板，5 台实机与 7 天观察均未证明。

v2.4.1 完成后才允许评审 v2.5。v2.5 的 MultiMaster-PKI、第二 Master、双向故障转移和 Ring 1 继续延期。

## 4. 目标状态机

### 4.1 Rollout State

`draft → waiting_approval → approved → batch_running → batch_observing → final_observing → awaiting_signoff → completed`

异常路径：

- 任意自动门禁失败：`batch_running|batch_observing|final_observing → paused`
- 人工终止：`paused|approved|batch_* → aborting → aborted`
- 回滚：`paused|batch_*|final_observing → rollback_running → rolled_back|rollback_failed`
- 系统错误：`* → failed`

禁止：

- `waiting_approval` 直接进入 `batch_running`。
- 未创建当前批次 Job 时 Advance。
- 当前批次存在非终态 Job 时 Advance。
- 任一 Target 非 `observing_passed` 时 Advance。
- 未完成 7 天窗口时进入 `awaiting_signoff`。
- 未完成三方最终签署时进入 `completed`。

### 4.2 Target State

`pending → preflight → dispatching → verifying → observing → observing_passed`

异常路径：

- `* → failed`
- `failed|observing → rollback_pending → rollback_running → rolled_back|rollback_failed`

所有状态变更必须带 `source_job_id`、`state_version`、`reason_code`、`observed_at` 与 Audit Event。

### 4.3 Job State

`queued → dispatching → running → result_pending → succeeded|failed|cancelled|expired`

规则：

- 已有 JID 永不重新 Publish。
- Poll 超时进入 `result_pending`，由 Reconciler 按 JID 查询。
- 只有 Salt 明确返回终态或超过可配置 Reconcile TTL 才进入 `failed/expired`。
- Terminal Job 不得被迟到 Return 覆盖。

## 5. 功能需求

### 5.1 单一 Ring 0 Aggregate

- Ring 0 API 与 Generic Rollout API 共享同一个 Domain Service 与 Transition Guard。
- Generic API 不得绕过 Ring 0 Approval、Batch、Observation 与 Signoff。
- 所有命令包含 `requestId`，使用数据库 Idempotency 与 Payload Digest。
- Rollout 使用 `state_version` 乐观锁，防止双 API/双 Worker 重复推进。
- Start、Evaluate、Advance、Pause、Resume、Rollback、Complete 全部写 Audit。

### 5.2 Target Snapshot Resolver

创建 Rollout 时由 Backend 解析 Target，不接受调用方自由拼装事实。

每个 Snapshot 固定：

- Endpoint ID、Minion ID、Tenant ID。
- Endpoint Group=`it|developer`。
- Machine/Device Identity Hash。
- Windows Account、SID、Profile、Hermes Home。
- Binding Revision、Pillar Revision。
- Release ID、Artifact SHA-256、Signing Key ID。
- Config Revision、Extension Version。
- Master ID=`192.168.102.104`。

创建门禁：

- 正好 5 个互不重复 Endpoint。
- Endpoint Active、Minion Key Accepted、`test.ping=True`。
- User Binding 完整且非 System。
- Release/Artifact Signature/Pillar/Config 可解析。
- Runtime Fallback Preflight 通过。
- Snapshot 规范化后计算 SHA-256；审批、Batch 与 Evidence 必须引用同一 Digest。

### 5.3 审批授权

- Approval Role 由 OIDC Claim 或 Management Backend RBAC 解析，禁止请求体自报。
- 需要三个不同 Subject：Release Owner、Platform Owner、Security Owner。
- 每个 Role 只能有一个有效 Approval。
- Approval 绑定 Snapshot Digest、Release、Config、Threshold Set 与过期时间。
- 任意上述内容变化，旧 Approval 自动失效。
- 最终 Signoff 与部署前 Approval 分表或分 `approval_stage` 保存。

### 5.4 Salt Job 与 Return Reconciliation

- 严格 Operation → Function 白名单，删除 `smc_hermes.*` 前缀通配。
- 修复生命周期映射：实现独立 `gateway_start/gateway_stop/gateway_restart`，或让统一入口显式支持并测试 `action`。
- `requested_by`、Audit Actor 只取认证 Principal；请求体字段废弃。
- 持久化 Redacted Salt Result、Result Schema Version、Function、Minion ID、Return Source 与 CapturedAt。
- Returner 必须验证 Device Endpoint = Return Endpoint = Job Minion Owner。
- Return Function 必须等于 Job 期望 Function。
- Poll 与 Returner 使用同一原子终态写入规则。
- 新增 Result Reconciler，服务重启后恢复 `running/result_pending` Job。
- `rollout_target_jobs` 支持 `handover/verify/rollback/remigrate` 多 Operation 与受控重试。

### 5.5 Production Handover Transaction

迁移步骤：

1. 读取并校验 Endpoint/User/Pillar/Release/Config。
2. 记录 Runtime Service、Runtime Gateway、Scheduled Task、Hermes Home、Owner、Release、Config Snapshot。
3. 验证 Salt Minion、Extension、Artifact Signature 与磁盘空间。
4. 准备 Salt 管理的 Hermes Release，不切换 Owner。
5. 停止旧 Gateway，并验证端口与进程已停止。
6. 禁用 Runtime Endpoint Ownership；必须操作真实 Service/Task，不只写 Marker。
7. 原子切换 Owner=`salt`。
8. 以绑定用户启动 `SMC Hermes Gateway` Task。
9. 验证 Gateway Health、Owner、Release、Config。
10. 执行 Work Critical Probe。
11. 写入 Migration Marker 与结构化 Return。

失败处理：

- Owner 切换前失败：保持 Runtime，不改变 Owner。
- Owner 切换后失败：执行完整 Snapshot Restore，恢复 Runtime Service/Task、旧 Gateway 与 Owner。
- 回滚必须分别验证 Runtime Control Plane 与 Work Data Plane。
- `runtime_reconcile()` 不得是固定成功 Stub。
- 只有恢复验证成功才能返回 `rolled_back`。

### 5.6 Batch Gate Evaluator

每个 Batch 必须满足：

- 当前批次已创建且 Target 数量符合 `1/2/2`。
- 每个 Target 的 Handover Job、Gateway Health、Owner、Release、Config、Work Probe 均成功。
- 每个 Target 已持续观察至少 24 小时。
- 当前窗口无 P0/P1、Owner Conflict、Secret Leak、Signature Bypass、Duplicate Publish。
- 当前批次所有 Target 都为 `observing_passed`。
- Operator 显式提交 Advance，且带最新 `state_version` 与 Evidence Digest。

任一条件失败：自动 `paused`，生成 Incident，拒绝新 Batch Job。

5 台样本下任何一台关键迁移或 Work Probe 失败均视为门禁失败，禁止用百分比掩盖单机失败。

### 5.7 Final 7-Day Gate

- Batch 3 通过后进入 `final_observing`，写真实 `final_observation_started_at/final_observation_due_at`。
- 必须连续 7×24 小时保留 5 台终端的有效样本。
- 数据缺口超过 5 分钟自动 Incident；无法证明的时间不得计入窗口。
- 7 天满足后进入 `awaiting_signoff`，不能自动 `completed`。
- Release、Platform、Security 三方最终签署完成后才能 `completed`。

### 5.8 Persistent Observation 与 Metrics

每 60 秒采集真实事实：

- Master/salt-api Availability。
- Minion Heartbeat 与 Key State。
- Gateway Health、进程、Task User。
- Control Owner。
- Current/Desired Release 与 Config Revision。
- Job 状态、Duration、Result Source。
- Work Critical Probe 结果。
- Returner Spool Depth 与 Last Flush。
- Owner Conflict、Secret Scan、Signature Validation。

按 15m、1h、6h、24h、7d 计算真实 Bucket Aggregate。服务重启后从 PostgreSQL 恢复窗口，不依赖进程内字典。

提供：

- `/salt/v1/ring0/rollouts/{id}/status`
- `/salt/v1/ring0/rollouts/{id}/gates`
- `/salt/v1/ring0/rollouts/{id}/observations`
- `/salt/v1/metrics` 或 Prometheus `/metrics`

### 5.9 Auto Pause

以下任一条件自动暂停：

- Master 连续不可用 180 秒。
- P0/P1 > 0。
- Secret Leak、Signature Bypass、Owner Conflict、Duplicate Publish > 0。
- 任一 Endpoint Heartbeat 缺失超过阈值。
- 任一 Gateway 或 Work Critical Probe 失败。
- Release/Config Drift。
- Job Terminal Failure 或 Return Identity Mismatch。
- Observation 数据缺口超阈值。

恢复后只允许人工 Resume。Resume 前必须重新 Evaluate Gates，并记录原因与审批人。

### 5.10 Evidence Bundle

输出目录：

`docs/salt/evidence/v2.4.1/ring0/<rollout-id>/<captured-date>/`

必须生成：

- `baseline.json`
- `target-snapshot.json`
- `approvals.json`
- `batches.json`
- `jobs.json`
- `job-returns.json`
- `observations.json`
- `metrics.json`
- `incidents.json`
- `rollback.json`
- `work-probes.json`
- `secret-scan.json`
- `manifest.json`
- `final-go-no-go.md`

规则：

- 每个 JSON 包含 `schemaVersion/capturedAt/source/status/digest`。
- `manifest.json` 保存所有文件 SHA-256、Git Commit、Rollout ID、Snapshot Digest、Release、Config 与生成器版本。
- Evidence Generator 只读取数据库与终端事实，禁止把缺失项填为通过。
- `implemented` 可由 CI 设置；`proven` 只能由授权人工签署。
- Secret Scan 非零时禁止生成 GO。
- Evidence 生成后写入只读归档；更改产生新 Bundle，不覆盖旧 Bundle。

### 5.11 Live Canary

- PowerShell 脚本与声明的 Windows PowerShell 5.1 兼容；如要求 PowerShell 7，显式改为 `#Requires -PSEdition Core`。
- TLS 验证使用受信 CA；Master Fingerprint 必须读取连接事实并与预期值比较。
- 校验 Minion Key、Extension Version、Pillar Revision、Release Signature、Config Revision。
- 变更操作只通过 Salt Control Job/Migration API。
- 等待 Job 终态或 `result_pending` Reconcile，不直接调用任意 Salt Function。
- 执行真实 Gateway 与 Work Critical Probe。
- Runtime Fallback 必须实际切换、验证、再 Remigrate；`WhatIf` 只能标为 `implemented`。
- 输出 Evidence Fragment 与 Digest，禁止记录 Token/Secret。

### 5.12 Work Critical Probe

每台终端验证：

- Work 在 Runtime `:8765` 停止时可启动。
- Salt Owner 下只做 Gateway Availability Probe，不安装、不更新、不重启 Gateway。
- Chat HTTP 与 WebSocket。
- Session 创建、继续与 History。
- Attachment Upload。
- Managed Files。
- Slash Command。
- Gateway 中断提示与恢复。
- Runtime Fallback 后 Work 可恢复。

- Live Canary 执行真实 Job、Work Probe、Rollback、Remigrate。
- 增加 `proven` 防伪 Guard。

退出：从一个测试 Rollout 自动生成 Schema Valid、Digest Valid、Secret-Free Bundle；缺失事实必为 `not_proven`。

### Phase 6：CI 与 Release Candidate

- Salt Control Ruff、Format、Pytest。
- PostgreSQL 16 Migration/Concurrency/Crash Recovery。
- Salt Extension Ruff、Pytest、Loader Contract。
- Returner Identity 与 Spool Recovery。
- OpenAPI/Client Contract Drift。
- Production Guard、Migration Coverage、Secret Scan。
- Work Ring 0 定向测试与 Windows Self-hosted Canary Dry Run。

退出：v2.4.1 Release Candidate 全绿；无 P0/P1；Live Runbook 已签署但实机 Evidence 仍由人工执行。

### Phase 7：Live Ring 0（人工执行）

1. 首台 Endpoint 预演 migrate → rollback → remigrate。
2. 冻结 5 台 IT/开发 Endpoint Snapshot。
3. 三方部署前审批。
4. Batch 1：1 台，观察至少 24 小时。
5. Batch 2：2 台，观察至少 24 小时。
6. Batch 3：2 台。
7. 受控执行 1 台 Endpoint Rollback，验证后 Remigrate。
8. 5 台连续观察 7 天。
9. 三方最终 Signoff。
10. 输出 v2.5 Go/No-Go。

退出：全部 Manual Gate=`proven`，Evidence Manifest 与签名有效，P0/P1=0。
