# 2. Hotfix 背景

v1.5 和 v1.5.1 已建立：

```text
RuntimeVersion
      ↓
HermesInstance
      ↓
GatewayProcessManager
      ↓
GatewayOwnershipService
      ↓
Gateway Health Worker
      ↓
Runtime Readiness
```

v1.5.1 又进一步增加：

```text
Persistent Fingerprint
Restart Reconcile
Safe Adoption
Orphan Prevention
```

最新代码中已经存在 `gateway_executable_path`、`gateway_command_hash`、`gateway_owner_runtime_id`、fingerprint version、`GatewayOwnershipService.inspect()`、`ADOPTED/CONFLICT` 等机制。

但运行仍出现：

```json
{
  "ownership": "conflict",
  "processState": "exited",
  "gatewayState": "healthy",
  "executionEligible": false,
  "reason": "GATEWAY_PORT_OWNERSHIP_CONFLICT"
}
```

同时：

```text
GET http://127.0.0.1:8642/health
HTTP 200
```

说明当前问题已经不是 Gateway Health，而是：

```text
Gateway API           Healthy
Gateway Process       实际仍存在
Runtime Ownership     无法证明
Runtime Process State 错判 exited
Execution             Blocked
```

---

# 3. 根因分析

v1.5.2 解决两个明确的实现缺陷。

## 3.1 Ownership 存在两套事实源

v1.5.1 新增：

```text
GatewayOwnershipService.inspect()
```

它能够判断：

```text
OWNED
ADOPTED
STALE
FOREIGN
UNKNOWN
CONFLICT
```

并支持 Persistent Fingerprint 与 Safe Adoption。

但 `InstanceGatewayService` 中仍保留旧：

```python
def _ownership_for(...):
    return verify_ownership(...)
```

并且至少以下核心运行路径仍使用旧逻辑：

```text
refresh_instance_status()
probe_and_recover()
```

Health Worker 当前仍：

```python
ownership = self._ownership_for(inst, exe_path)

process_exited =
    desired == RUNNING
    and not ownership.owned
    and not tracked_alive
```

这意味着一个已经被 v1.5.1 认领为：

```text
ownership=adopted
```

的 Gateway，在下一次周期 Health Worker 中仍可能因为旧 `verify_ownership()` 不能确认 `owned` 而被重新判为：

```text
process=exited
```

并触发：

```text
GATEWAY_PORT_OWNERSHIP_CONFLICT
```

### 结论

> **Gateway Ownership 必须只有一个 SOT：`GatewayOwnershipService.inspect()`。**

业务 Service 不允许继续直接使用 `verify_ownership()`。

---

# 3.2 当前 Fingerprint 错误假设 `spawn PID == listener PID`

`GatewayProcessManager.start()` 当前通过：

```python
asyncio.create_subprocess_exec(...)
```

启动 Hermes，然后立即把：

```text
process.pid
```

保存为 Gateway PID，并基于这个 PID 捕获 fingerprint。

旧 ownership 验证同时要求：

```text
stored PID
==
PID listening on gateway_port
```

否则判断为 foreign/conflict。

但是 Gateway 真实进程模型可能是：

```text
Runtime
   │
   ▼
Hermes Launcher PID A
   │
   ▼
Hermes/Python Listener PID B
   │
   ▼
127.0.0.1:8642
```

此时：

```text
stored PID       = A
8642 listener    = B
```

于是当前 Runtime 会错误得到：

```text
A != B
→ ownership conflict
```

即使：

```text
B /health = 200
```

且 B 实际正是 A 启动出的合法 Hermes Gateway。

# 8. Launcher Identity

Launcher 表示：

```text
Runtime 通过 create_subprocess_exec()
直接创建的进程
```

例如：

```text
hermes gateway run --external-supervisor
```

保存：

```text
launcher_pid
launcher_create_time
```

Launcher 主要用于：

```text
首次启动时建立 process lineage
```

Runtime reload 后：

> Launcher 不要求继续存在。

---

# 9. Listener Identity

Listener 才是 Hermes Gateway Supervisor 的主要 Process Identity。

定义：

```text
listener_pid
listener_create_time
listener_executable_path
gateway_port
```

其必须满足：

```text
PID alive

AND

PID listening gateway_port

AND

create_time matches

AND

Gateway authenticated health succeeds
```

Runtime 重启后的 Ownership Recovery 应主要使用：

```text
Listener Identity
```

而不是 Launcher PID。


可以检查：

```text

```

但：

```text
InstanceGatewayService
GatewayHealthWorker
RuntimeStatusService
```

不得直接调用。

# 24. 删除 `_ownership_for()`

当前：




# 30. Safe Adoption v2

不能继续单纯要求：


# 36. Health Worker 新流程

每个 tick：

```text

      ↓
GatewayOwnershipService.inspect()
      ↓
Update ownership observed state
      ↓
Update process state
      ↓
Update API health
      ↓
Calculate execution eligibility
      ↓
Decide recovery
```

---

# 37. `not owned != exited`

这是 v1.5.2 硬规则。

以下状态：

```text
UNKNOWN
FOREIGN
CONFLICT
```

均：

```text
!= EXITED
```

只有：

```text
Listener PID explicitly missing/dead
```

或者：

```text
Fingerprint confirmed STALE
```

才能：

```text
process_state=exited
```

---

# 38. Process State 新语义

推荐：

```text
starting
alive
exited
foreign
unknown
```

当前场景正确状态应该是：

```text
Process       Alive / Unknown ownership
Gateway       Healthy
Ownership     Conflict
```

而不是：

```text
Process       Exited
Gateway       Healthy
```

后者本身就是状态矛盾。

---

# 39. Ownership 与 Process State 分离

例如：

### Healthy + owned

```text
process=alive
ownership=owned
gateway=healthy
```

### Healthy + adopted

```text
process=alive
ownership=adopted
gateway=healthy
```

### Healthy + conflict

```text
process=alive
ownership=conflict
gateway=healthy
```

### Gateway truly exited

```text
process=exited
ownership=stale
gateway=unreachable
```

---

# 40. Execution Eligibility

继续保持：

```text
executionEligible
=
Gateway Healthy
AND
Ownership ∈ {owned, adopted}
```

不放宽 v1.5 安全边界。

```text

```

> 当前永久状态。

# 97. v1.5.2 六个硬性验收指标

1. **Hermes Launcher PID 与 8642 Listener PID 不一致时，不得再自动产生 `GATEWAY_PORT_OWNERSHIP_CONFLICT`。**

2. **`GatewayOwnershipService.inspect()` 成为唯一 Ownership SOT；`InstanceGatewayService` 和 Health Worker 不再直接调用旧 `verify_ownership()`。**

3. **一个已经 `ADOPTED` 的 Gateway，在 `refresh_instance_status()` 和周期 Health Worker 后仍保持 `ADOPTED / Healthy`。**

4. **`ownership != owned` 不再自动推导 `process=exited`；只有 Listener PID 被确认消失或 fingerprint stale 才能标记 `exited`。**

5. **历史 `GATEWAY_PORT_OWNERSHIP_CONFLICT` 在当前 ownership 已恢复时自动清除，不再导致每 5 秒 `gateway.recovery.failed`。**

6. **整个 Hotfix 不修改 Chat / Task 执行逻辑；默认 Instance 恢复 `executionEligible=true` 后 Chat 自然恢复。**

## 98. 最终实施重点

v1.5.2 不应该继续围绕：

```text
怎样让 conflict 更容易变成 adopted
```

继续增加条件。

真正需要修正的是两层模型：

```text
旧模型：
Gateway = 一个 PID

新模型：
Gateway =
Launcher Process
+
Listener Process
+
Authenticated API
+
Runtime Ownership
```

同时彻底解决：

```text
旧 verify_ownership
+
新 GatewayOwnershipService
```

两套 Ownership SOT 并存的问题。

当前源码已经具备 v1.5.1 的 Persistent Fingerprint、Safe Adoption 与 Reconcile 框架，但 `refresh_instance_status()` / Health Worker 仍有旧 Ownership 路径，而 `GatewayProcessManager` 仍以 spawn PID 建立进程指纹。

**因此 v1.5.2 的验收重点不是“8642 `/health` 能返回 200”——这一项现在已经通过；而是 Runtime 必须能够稳定回答：“实际监听 8642 的进程是谁，它与我启动的 Hermes Gateway 有什么可验证关系，并且在 reload 后仍能恢复这一关系。”**
