# 2. 版本背景

v1.5.3 完成后，当前链路已经验证：

```text
Runtime :8765
    ↓
Default Hermes Instance
    ↓
Gateway :8642
    ↓
API_SERVER_KEY authentication
    ↓
Hermes Agent
    ↓
LLM
    ↓
SSE
```

Postman 已能够成功执行：

```http
POST /api/v1/instances/{instanceId}/chat/completions
```

并收到完整 SSE 事件和：

```text
chat.done
```

因此可以确认：

```text
Runtime                     OK
Hermes Instance             OK
Gateway Ownership           OK
Gateway Authentication      OK
Hermes Chat                 OK
SSE                         OK
```

本版本不再处理 Gateway 生命周期问题。

当前剩余两个问题：

1. Runtime `/chat/models` 返回的是 `smc-copilot` Gateway 虚拟模型，而不是真实 Hermes 可用模型与当前默认模型。
2. Desktop 虽然已经存在 `ServeChatRuntimeAdapter`，但 Runtime Connection Gate 仍可能停留在 `RuntimeStarting`，导致 Chat 无法进入已经验证成功的 Runtime SSE transport。

# 3. 当前问题一：Model Catalog 语义错误

当前 Runtime：

```text
GET /instances/{id}/chat/models
        ↓
InstanceChatService.list_models()
        ↓
HermesGatewayClient.list_models()
        ↓
GET Hermes /v1/models
```

`InstanceChatService` 当前确实直接把 Hermes `/v1/models` 返回的数据包装成 `ChatModel`。

但 Hermes 当前明确区分了两个接口：

```text
/v1/models
```

是 OpenAI-compatible compatibility surface，只暴露 Hermes Agent 的虚拟模型名称；真正面向 Hermes UI 的 Provider / Model picker 应使用：

```text
/api/model/options
```

后者返回 provider-aware 模型目录、模型能力与相关 picker 信息。

因此：

```text
smc-copilot
```

不是错误的 Hermes Gateway 返回值。

错误在于：

> **SMC Runtime 把 Gateway Virtual Model 当成了用户模型目录。**

# 4. 当前问题二：model-config 被虚拟模型污染

当前 `ensure_default_model_config()`：

```text
优先 /v1/models 第一项
↓
保存 profile_chat_settings

失败后才 fallback config.yaml
```

因此：

```text
/v1/models
→ smc-copilot
```

最终写成：

```json
{
  "provider": "hermes",
  "model_id": "smc-copilot"
}
```

源码明确采用这一优先级。

这与产品语义不符。

`smc-copilot` 应定义为：

```text
Gateway Virtual Model
```

而用户看到的：

```text
Current Model
```

应定义为 Hermes 当前真正执行的：

```text
Provider + Model
```

# 5. 当前问题三：Desktop Chat 已有 Runtime Adapter，但被 Connection Ready Gate 阻断

Desktop 当前已经实现：

```text
Chat UI
  ↓
chat-runtime-ipc
  ↓
ServeChatRuntimeAdapter
  ↓
chatRuntimeClient
  ↓
Runtime /chat-runs
  ↓
Runtime SSE
```

`chat-runtime-ipc.ts` 已经明确优先使用 `ServeChatRuntimeAdapter`，并在 Runtime 不 Ready 时 Fail Closed。

`ServeChatRuntimeAdapter` 也已经完整实现：

```text
resolve instance
create run
create turn
subscribe SSE
map event
abort
snapshot
replay
queue
interaction response
```

Desktop Chat Runtime client 已经通过：

```text
POST /chat-runs
POST /chat-runs/{run}/turns
GET /chat-runs/{run}/events/stream
```

实现 Runtime SSE。

所以：

> **Desktop Chat transport 不需要推倒重写。**

当前真正需要关闭的是：

```text
Desktop Runtime Connection State
        ↓
Ready=false
        ↓
ServeChatRuntimeAdapter.ready=false
        ↓
Chat blocked
```

# 66. v1.5.4 最终验收标准

必须同时满足：

1. `GET /instances/{id}/chat/models` 返回 Hermes **真实可用 Provider/Model 列表**，不再只返回 `smc-copilot`。
2. `/v1/models` 中的 `smc-copilot` 只作为 Gateway Virtual Model 使用。
3. `GET /chat/model-config` 返回 Hermes `config.yaml` 当前真实默认 Provider/Model。
4. 历史 `provider=hermes/model_id=smc-copilot` 数据完成自动 reconcile。
5. Desktop 启动不再尝试 spawn Runtime。
6. Desktop 能稳定识别已经运行的 `127.0.0.1:8765`。
7. `maintenance.ready=false` 不得阻塞 Chat。
8. Chat Enable 由 `execution.chatReady` 控制。
9. Desktop Chat 正常发送后必须进入 `ServeChatRuntimeAdapter`。
10. Desktop Chat 使用 Runtime `/chat-runs` + SSE，正常路径不得直连 Hermes `:8642`。
11. SSE delta、tool progress、terminal event、`chat.done` 可以正常映射到现有 Chat UI。
12. Postman 与 Desktop 使用的是同一条 Runtime → Hermes Chat execution 链路。

**v1.5.4 的核心不是再修 Runtime Gateway，而是把已经验证正常的 Runtime 能力正式接给 Desktop，同时修正 Model Catalog 的语义。** 当前代码已经具备 Runtime ChatRun/SSE 的主要实现，重点应放在 `Model SOT + Connection/Readiness Gate + Transport Closure`，避免再次扩张 Hotfix 范围。
