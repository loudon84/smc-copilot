# 2. 版本背景

v1.5.2 已经基本解决 Gateway Process Ownership。

当前 Runtime 日志已经能够稳定识别：

```text
gateway.ownership.inspect
health_ok=True
listener_pid=34064
source=listener-fingerprint
state=adopted
```

同时：

```text
GET http://127.0.0.1:8642/health
→ HTTP 200
```

说明以下链路已经成立：

```text
Runtime
   ↓
Gateway Listener
   ↓
:8642
   ↓
/health
   ↓
200 OK
```

因此当前故障已经不再是：

```text
Gateway Process Ownership
Gateway Listener Identity
Gateway Reachability
```

而是在调用受认证接口：

```http
GET /v1/models
```

时 Hermes 返回：

```text
API server rejected invalid API key
```

当前故障链变为：

```text
Runtime
   │
   │ Authorization:
   │ Bearer <Runtime API_SERVER_KEY>
   ▼
Hermes Gateway
   │
   X
API_SERVER_KEY mismatch
   │
   ▼
401 / invalid API key
```

# 3. 当前源码问题

## 3.1 Runtime 自己维护了一套 `API_SERVER_KEY`

当前 `SecretService.ensure_api_server_key()` 的行为是：

```text
Runtime SecretStore
      ↓
检查 API_SERVER_KEY
      ↓
不存在
      ↓
secrets.token_urlsafe(32)
      ↓
生成新 API_SERVER_KEY
      ↓
保存 Runtime SecretStore
```

也就是说 Runtime 当前把自己当成了 Gateway Credential 的配置源。

Instance 启动时又会执行：

```python
await SecretService(...).ensure_api_server_key(inst.profile_name)
```

随后 `_resolve_secrets()` 从 Runtime DB `SecretReference` + Runtime SecretStore 获取 Key。

---

# 4. Runtime Gateway Client 同样读取 Runtime SecretStore

当前：

```text
HermesGatewayClientFactory
       ↓
GatewayCredentialService
       ↓
SecretReference
       ↓
SecretStore
       ↓
API_SERVER_KEY
```

`GatewayCredentialService.resolve_api_server_key()` 并没有读取 Hermes 自己的 `.env`。

因此当前存在两个 Credential SOT：

```text
Hermes SOT
~/.hermes/.env
API_SERVER_KEY=A
```

以及：

```text
Runtime SOT
Runtime SecretStore
API_SERVER_KEY=B
```

---

# 5. 为什么 `/health` 正常，而 `/v1/models` 失败

Hermes 的：

```http
GET /health
```

属于公开 liveness probe。

因此：

```text
API_SERVER_KEY 不一致
```

并不会影响：

```text
/health → 200
```

但：

```http
GET /v1/models
```

需要：

```http
Authorization: Bearer <API_SERVER_KEY>
```

Hermes 官方 API Server 配置也明确要求在默认 Profile：

```text
~/.hermes/.env
```

配置：

```env
API_SERVER_ENABLED=true
API_SERVER_KEY=...
```

客户端再使用相同 Key 访问 Gateway。

所以当前很可能是：

```text
~/.hermes/.env
KEY=A
       ↓
Hermes Gateway

Runtime SecretStore
KEY=B
       ↓
HermesGatewayClient

B != A
       ↓
invalid API key
```

---

# 6. 另一个关键问题：Hermes 会重新加载自己的 `.env`

即使 Runtime 启动 Hermes Gateway 时注入：

```text
API_SERVER_KEY=B
```

Hermes 自己仍会加载 profile `.env`。

Hermes 当前 `load_hermes_dotenv()` 使用用户 `.env`，并以 `override=True` 加载。

因此实际有可能发生：

```text
Runtime Child Environment
API_SERVER_KEY=B
        ↓
启动 Hermes
        ↓
Hermes load ~/.hermes/.env
        ↓
API_SERVER_KEY=A
```

最终 Gateway 使用：

```text
A
```

而 Runtime Client 继续使用：

```text
B
```

这就是当前架构必须修复的根本问题。

本版本正式确立：

> **Hermes 本地配置属于 Hermes，Runtime 是 Hermes Supervisor，不是 Hermes Configuration Owner。**

职责重新定义：

```text

负责：
.env
config.yaml

```

Runtime 不再维护一套独立的 Hermes Gateway Credential 真相。

# 12. Default Profile 收敛

Hermes 本身支持多个 Profile。

默认 Profile 使用：

```text
~/.hermes/
├── .env
├── config.yaml
└── SOUL.md
```

named profile 才使用：

```text
~/.hermes/profiles/<name>/
```

Hermes 官方多 Profile 文档明确区分了这两类目录。

但 SMC Copilot 当前阶段正式限定：

```text
Local Hermes Profile = default
```

# 114. v1.5.3 八个硬性验收指标

1. **Local default Hermes 的 `API_SERVER_KEY` 必须从 `~/.hermes/.env` 获取。**

2. **External/Development Hermes 缺少 API_SERVER_KEY 时必须 Fail Closed，Runtime 不得再生成随机 Key。**

3. **Gateway Process 和 `HermesGatewayClientFactory` 必须通过同一个 Credential Resolver 获取同一 Key。**

4. **Runtime SecretStore 中即使残留旧 `API_SERVER_KEY`，Local Hermes 也不得使用它覆盖 `.env`。**

5. **`GET /v1/models` 必须通过 Hermes Gateway 鉴权，不再产生 `API server rejected invalid API key`。**

6. **Local Runtime 只允许 `default` Profile：`~/.hermes/.env + ~/.hermes/config.yaml + :8642`。**

7. **Runtime Diagnostics 可以显示 Key 来源、配置状态、Fingerprint 和 Authentication 状态，但任何 API/日志不得暴露真实 Key。**

8. **本版本不修改 Chat/Task 业务逻辑；Postman Runtime Chat 调试通过后，再恢复 Desktop 对接。**

## 115. 本版本最终边界

v1.5.3 之后需要正式固定三层 Ownership：

```text
Hermes owns
│
├─ ~/.hermes/.env
├─ ~/.hermes/config.yaml
├─ Provider credentials
├─ API_SERVER_KEY
└─ Agent configuration


Runtime owns
│
├─ Hermes RuntimeVersion
├─ HermesInstance
├─ Gateway lifecycle
├─ Gateway process ownership
├─ Gateway health/authentication
├─ Gateway API client
└─ Runtime API :8765


Desktop owns
│
├─ UI
├─ Runtime API invocation
└─ Runtime status/log/diagnostic presentation
```

这里最关键的变化是：

> **“Runtime 管理 Hermes Gateway”不再等价于“Runtime 管理 Hermes 配置”。**

当前代码已经有正确的 `HERMES_HOME`、default profile 路径以及 `HermesGatewayClientFactory` 边界，但 Credential 仍从 Runtime SecretStore 获取，并且 `SecretService.ensure_api_server_key()` 会在缺失时自行生成 Key；这正是 v1.5.3 要关闭的最后一条配置分叉。

**建议 Cursor 严格先完成 Phase 1～7，并用 Postman 验证 `/chat/models` 和 Runtime Chat 完整通过；在此之前不要继续修改 Desktop。**
