# 一、现有功能的关键缺口

## 1. Clarify / Approval 仍是兼容性 Follow-up，不是原生继续执行协议

当前 `HermesChatCommandAdapter` 并没有调用 Hermes 的原生 Clarify 或 Approval API，而是构造：

```text
[[hermes.clarify.response]]
[[hermes.approval.response]]
```

然后向 `/v1/chat/completions` 重新提交一条普通 User Message。请求使用 `stream: false`，并且代码只检查 HTTP 状态，不读取和处理成功响应内容。

因此目前所谓“真执行”实际表示：

```text
UI Command
→ HTTP 2xx
→ 标记 interaction resolved
```

并不能保证：

* Hermes 将该消息识别为原请求的 Clarify 回答；
* Approval 真正恢复了暂停中的 Tool Call；
* Deny 真正取消了原 Tool Call；
* 继续执行的 Agent 响应进入当前 Chat；
* 原 Model、Expert、Skill、Tool Context 被保留；
* 后续 Token、Tool Event、Reasoning 继续回传。

这套实现可以保留为兼容路径，但不能作为生产级 Human-in-the-loop 主协议。

---

## 2. Follow-up 响应不会回流 Chat

`postContinuationMessage()` 使用：

```ts
stream: false
```

HTTP 成功后直接结束，没有读取 response body，也没有转换为：

* `message.delta`
* `reasoning.delta`
* `tool.event`
* `usage`
* `completed`

Main 随后立即发送：

```text
clarify.resolved
approval.resolved
```

但用户看不到 Hermes 对该回答的后续处理结果。

---

## 3. Pending Interaction 仍依赖 Active Run 内存对象

Pending Interaction 保存在：

```ts
ChatRunHandle.pendingInteractions: Map
```

而 `ChatRunHandle` 本身只存在于 Main Process 内存 `activeRuns` Map 中。

一旦出现以下情况，Pending Interaction 会丢失：

* 应用重启；
* Renderer Reload；
* Main Process 重启；
* Run 被清理；
* 原 Stream 提前结束；
* 用户较晚才处理 Approval。

---

## 4. Turn 完成时会直接删除 Active Run

`finishOnce()` 当前执行：

```ts
stopSessionReconcile(runId);
clearActiveRun(runId);
resolveChat(result);
```

如果 Hermes 在发出 `clarify.requested` 或 `approval.requested` 后关闭当前 Stream，随后触发 `onDone`，Run 会从 Registry 删除。

用户之后点击操作时将得到：

```text
RUN_NOT_FOUND
```

Command Handler 确实要求 `getActiveRun(runId)` 必须存在。

因此必须将：

```text
网络 Transport Handle
```

与：

```text
Run / Turn / Pending Interaction 状态
```

拆分管理。

---

## 5. Queue 的 dequeue 实现存在可靠性风险

当前 `dequeue()` 通过：

```ts
let next;
setQueue(prev => {
  next = prev[0];
  return prev.slice(1);
});
return next;
```

返回队首元素。

这个实现依赖 React State Updater 在函数返回前同步执行，不是可靠的原子出队契约。结果可能是：

```text
Queue 有数据
→ dequeue() 返回 undefined
→ 消息已经或尚未从 State 删除
→ 自动 Drain 中断
```

Queue 应改为 Reducer、Ref-backed Store 或独立 Workspace Store。

---

## 6. Retry 仍然只关联“最后一轮”

Controller 当前只保存：

```ts
lastTurnSnapshotRef
lastTurnSnapshot
```

没有建立：

```text
turnId → request snapshot
turnId → response
turnId → error message
```

的完整映射。

因此当会话中出现多个失败 Turn 时，任意 Error Card 的 Retry 都可能重放最后一次 Turn，而不是该 Error 对应的 Turn。

---

## 7. Retry 会重复追加 User Message

`retryLastTurn()` 调用 `submitPayload()` 时没有设置：

```ts
skipAppendUser: true
```

而 `submitPayload()` 默认重新追加：

* User Message；
* Pending Assistant Message。

结果可能是：

```text
用户原消息
失败提示
用户原消息（重复）
新 Assistant
```

这不符合“重新生成上一条回答”的语义。

---

## 8. Edit and Retry 没有恢复完整 Work Context

当前 `editAndRetryLastTurn()` 只恢复：

* 输入文本；
* 附件；
* Model。

没有恢复：

* Expert；
* Team；
* Skill；
* Work Mode；
* Permission；
* Prompt Hint；
* Invocation Source。

虽然 Snapshot 保存了部分字段，但 Controller 没有调用 Workspace Context 更新接口。

---

## 9. Turn Snapshot 仅存在于 Renderer 内存

当前 Snapshot：

* 不持久化到数据库；
* 不写入 Session；
* 应用重启后丢失；
* 无法恢复 Queue；
* 无法恢复 Retry；
* 无法审计某次请求实际使用了哪个 Model、Expert 和 Prompt Hint。

---

## 10. Electron E2E 仍未建立

`package.json` 中仍没有：

* `@playwright/test`
* `test:e2e:electron`
* Electron Test Harness
* Screenshot Regression
* E2E CI Gate

当前 CI 只执行 Vitest、TypeScript 和 Build。

因此目前无法自动证明：

* Main、Preload、Renderer 契约真实连通；
* Clarify 后有继续输出；
* Approval 后 Tool 真正执行；
* 多 Run 和 Queue 不串流；
* 应用重启后状态可恢复；
* 浮动按钮坐标稳定；
* 文件 Badge 与 Panel 内容一致。

# 4. Chat Submit 改为事件驱动

## 4.1 当前问题

目前：

```text
ipcRenderer.invoke(chat-runtime:submit)
```

需要等待整个 Agent Turn 完成后才返回。

对于：

* 长任务；
* Approval；
* Clarify；
* 多 Tool；
* 网络恢复；

这种长时间 Invoke 不适合作为 Runtime 主生命周期。

---

## 4.2 新契约

新增：

```ts
export type ChatStartInput = {
  runId: string;
  turnId: string;
  request: ChatTurnRequestSnapshot;
};

export type ChatStartResult =
  | {
      ok: true;
      runId: string;
      turnId: string;
      acceptedAt: number;
    }
  | {
      ok: false;
      code: string;
      error: string;
    };
```

调用流程：

```text
Renderer
→ chat-runtime:start
→ Main 校验并持久化 Turn
→ 立即返回 accepted
→ 后续全部通过 chat-runtime:event 返回
```

不再等待完整 Response 才完成 IPC。

---

## 4.3 Channel 调整

```ts
CHAT_RUNTIME_CHANNELS = {

  abort: "chat-runtime:abort",

  event: "chat-runtime:event"
```

旧 `submit` 保留一个版本作为 Compatibility Adapter，生产 Chat 不再调用。

---

## 7.2 执行优先级

### 第一优先级：Hermes 原生 Interaction API

启动时探测 Gateway Capability：

```text
clarify_response
approval_response
session_continuation
```

存在原生接口时直接调用。

### 第二优先级：流式 Session Continuation

使用现有 `sendMessage()` 运行链路，而不是当前的 `fetch(stream:false)`。

必须：

* Resume 相同 Session；
* 使用相同 Profile；
* 使用相同 Model；
* 保留 Work Context；
* 继续发送 SSE；
* 继续产生 Tool Event；
* 继续产生 Usage；
* 最终发送 Completed。

### 第三优先级：明确失败

Gateway 不支持时返回：

```text
GATEWAY_UNSUPPORTED
```

禁止静默模拟成功。

---

## 7.3 Interaction 事件语义

新增：

```ts
interaction.accepted
interaction.continuing
interaction.resolved
interaction.failed
```

语义：

```text
accepted
= Main 接受了用户命令

continuing
= Gateway 已确认并开始继续执行

resolved
= Interaction 已完成处理

failed
= 命令或继续执行失败
```

不得在 HTTP 2xx 后立即把整个 Interaction 标记为 Resolved。

# 10. Retry 语义修复

## 10.1 Retry

操作对象必须是：

```text
该 Error Card 对应的 turnId
```

流程：

```text
查找 Turn Record
→ 删除或替换失败 Assistant/Error
→ 保留原 User Message
→ 创建新 Turn
→ 使用原 Request Snapshot
```

不得再次追加相同 User Message。

## 10.2 Edit and Retry

恢复：

* 文本；
* 附件；
* Model；
* Expert；
* Team；
* Skill；
* Work Mode；
* Permission；
* Prompt Hint。

恢复后不自动发送。

## 10.3 Retry with Current Context

保留：

* 原文本；
* 原附件。

使用当前：

* Model；
* Expert；
* Skill；
* Work Mode；
* Permission；
* Prompt Hint。

# 11. Queue Store 重构

## 11.1 禁止从 React State Setter 返回出队值

改为 Reducer：

```ts
type QueueAction =
  | { type: "enqueue"; entry: QueuedChatTurn }
  | { type: "remove"; queueId: string }
  | { type: "move"; from: number; to: number }
  | { type: "mark_running"; queueId: string }
  | { type: "complete"; queueId: string };
```

自动 Drain 从当前 State 明确读取：

```ts
const next = queue[0];
```

之后 Dispatch：

```text
mark_running
```

不再使用当前 `dequeue()` 返回局部变量的实现。

---

## 11.2 Queue 功能

支持：

* 删除；
* 修改文本；
* 查看附件；
* 拖动排序；
* 立即执行；
* 暂停自动 Drain；
* 应用重启恢复；
* Run 关闭时确认处理 Queue。

---

## 11.3 Queue 状态

```text
queued
running
completed
failed
cancelled
```

只有 `queued` Entry 会被自动执行。

# 12. Runtime Recovery

## 12.1 应用启动

Main Process：

```text
读取 chat_runtime_turn
→ 找到 starting / streaming / waiting 状态
→ 查询 Session DB 与 Gateway
```

处理规则：

* Session 已完成：恢复为 Completed；
* 存在 Pending Interaction：恢复 Waiting Card；
* Transport 已断开但 Session 未完成：标记 Interrupted；
* Queue 尚未执行：恢复 Queue；
* 不自动重放失败 Turn。

---

## 12.2 Renderer Reload

Renderer 重新挂载后调用：

```text
chat-runtime:get-state
```

恢复：

* Run；
* Turn；
* Partial Messages；
* Pending Interaction；
* Queue；
* Usage；
* 当前状态。

## E2E-03 Application Restart

```text
出现 Approval
→ 关闭应用
→ 重新打开
→ Pending Approval 恢复
→ Approve
→ 继续执行
```

## E2E-04 Queue

```text
Turn A streaming
→ 排队 B、C
→ 调整 C 到 B 前
→ A completed
→ C 执行
→ B 执行
```

## E2E-05 Retry

```text
Turn A failed
→ Retry
→ 不重复 User Message
→ 使用原 Model 和 Expert
```

## E2E-06 Multi-Run

```text
Run A waiting approval
Run B streaming
Run C queued
→ 三者状态互不影响
```

# 22. 验收标准

## Runtime

* Start 立即返回；
* Event 有唯一 ID 和递增 Sequence；
* Main 与 Renderer 可恢复状态；
* Pending Interaction 不依赖网络 Handle；
* 应用重启后可继续审批；
* 同一 Event 不重复应用。

## Interaction

* Clarify 后有继续输出；
* Approval 后 Tool 真执行；
* Deny 后 Tool 不执行；
* Interaction 不因 Stream 结束变成 `RUN_NOT_FOUND`；
* Gateway 不支持时明确报错。

## Queue

* 出队操作原子可靠；
* Queue 可排序、删除和暂停；
* 附件、Model、Expert 不丢失；
* 应用重启后 Queue 恢复。

## Retry

* Retry 不重复 User Message；
* Retry 精确对应 Error Turn；
* Edit and Retry 恢复完整 Work Context；
* Retry with Current Context 使用当前配置。
