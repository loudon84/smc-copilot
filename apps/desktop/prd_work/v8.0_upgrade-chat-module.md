# copilot-desktop Chat 模块迁移到 ai-os-desktop 方案

## 1. 迁移结论

不建议执行：

```text
references/copilot-desktop/src/renderer/src/screens/Chat
  → 直接覆盖
src/renderer/src/screens/Hermes/pages/Chat
```

原因是两个项目的 Chat 已经形成不同架构：

* `copilot-desktop` 的 Chat 是一个完整垂直功能切片，包含多会话运行、流式事件、Reasoning、Tool、Clarify、附件、Session Files、文件预览、模型覆盖、Slash Command、消息队列、后台问题等能力。`Chat.tsx` 直接依赖大量 Renderer、Shared、Preload 和 Main 模块，并非独立页面。
* `ai-os-desktop` 已经存在 `screens/Hermes/pages/Chat`，并集成 Work Expert、Expert Team、MCP、任务状态、Profile Runtime 等业务能力。当前入口是 `HermesDefaultChatPage → HermesDefaultWebChatSurface`。
* `ai-os-desktop` 强制遵循 `Main → IPC → Preload → index.d.ts → Renderer` 的跨进程契约，不能让迁移后的组件继续任意访问旧项目 API。

推荐采用：

```text
Copilot Chat Module
        +
AI-OS Chat Adapter
        +
现有 Work / Expert / MCP Host
```

即：**源项目 Chat 作为 UI 与交互内核，目标项目继续负责 Runtime、Profile、Work、Expert、MCP、WebOperator 和 Shell。**

---

## 2. 两个项目的 Chat 架构差异

### 2.1 copilot-desktop Chat

源 Chat 的核心结构是：

```text
Layout
└─ ChatRun Manager
   ├─ Chat runId=A
   ├─ Chat runId=B
   └─ Chat runId=C
```

每个 `Chat` 都保持挂载，只隐藏非活跃会话。源项目通过 `runId` 区分并发会话，支持后台会话继续运行。

Chat 内部主要包含：

```text
Chat.tsx
├─ ChatInput
├─ MessageList
│  ├─ MessageRow
│  ├─ ReasoningRow
│  ├─ ToolActivityGroup
│  └─ ClarifyCard
├─ ModelPicker
├─ ReasoningEffortPicker
├─ QueuedMessages
├─ ContextFolderChip
├─ WorktreePanel
├─ SessionFilesPanel
├─ FilePreviewPanel
└─ WebPreviewPanel
```

`MessageList` 已经把连续 Tool Call/Result 合并为 Tool Activity Group，并独立处理 Reasoning、Clarify、Agent Bubble 和加载状态。

其流式处理能力包括：

```text
chat-session-started
chat-chunk
chat-reasoning-chunk
chat-tool-progress
chat-tool-event
clarify-request
chat-usage
chat-done
chat-error
```

`useChatIPC` 会按 `runId` 过滤事件，并在运行中每 750ms 从 Session DB 回补 Reasoning、Tool Result 等持久化内容。

### 2.2 ai-os-desktop 当前 Chat

目标 Chat 当前结构为：

```text
HermesDefaultChatPage
└─ HermesDefaultWebChatSurface
   ├─ HermesActiveExpertBar
   ├─ TaskStatusBar
   ├─ WorkChatContextBar
   ├─ PromptHintComposer
   ├─ ChatScrollArea
   ├─ WorkComposerControls
   └─ ComposerBar
```

它已经承载：

* 当前 Expert / Expert Team
* Work Permission
* Profile
* MCP Expert Gateway
* Task 状态与执行时间
* Expert Prompt Hint
* Agent 输出文档识别

这些能力不能被源 Chat 覆盖掉。

目标项目当前的主要不足是流事件仍为全局通道：

```text
chat-chunk
chat-done
chat-error
chat-tool-progress
chat-usage
```

事件没有 `runId`；Main 侧也只有一个 `chatAbortRef.current`。当多个会话并发运行时，容易发生消息串流、错误会话被取消、Tool Progress 写入错误页面等问题。

因此，迁移的第一优先级不是 UI，而是：

```text
单会话全局 Chat IPC
        ↓
runId 隔离的 Chat Runtime IPC
```

## 5. Chat Runtime 新契约

建议定义统一输入：

```ts
export interface ChatSubmitInput {
  runId: string;
  profileId: string;
  sessionId?: string;

  message: string;
  history: ChatHistoryMessage[];
  attachments?: ChatAttachmentRef[];
  contextFolder?: string;
  model?: ChatModelOverride;

  expertId?: string;
  teamId?: string;
  expertRunId?: string;
  workMode?: string;
  invocationSource:
    | "default_chat"
    | "expert_chat"
    | "team_chat";
}
```

统一事件：

```ts
export type ChatRuntimeEvent =
  | { type: "session.started"; runId: string; sessionId: string }
  | { type: "message.delta"; runId: string; content: string }
  | { type: "reasoning.delta"; runId: string; content: string }
  | { type: "tool.progress"; runId: string; tool: string }
  | { type: "tool.event"; runId: string; event: ChatToolEvent }
  | { type: "clarify.requested"; runId: string; request: ClarifyRequest }
  | { type: "approval.requested"; runId: string; request: ApprovalRequest }
  | { type: "usage"; runId: string; usage: ChatUsage }
  | { type: "completed"; runId: string; sessionId?: string }
  | { type: "failed"; runId: string; error: ChatRuntimeError }
  | { type: "cancelled"; runId: string };
```

Main 侧由：

```ts
const activeRuns = new Map<string, ChatRunHandle>();
```

替代：

```ts
const chatAbortRef = {
  current: null
};
```

并将所有推送事件从：

```ts
event.sender.send("chat-chunk", chunk);
```

改为：

```ts
event.sender.send("chat-runtime:event", {
  type: "message.delta",
  runId: input.runId,
  content: chunk,
});
```

目标项目的 Expert Run Bridge 仍在 Main 层执行：

```text
beforeExpertChatSend
bridgeChatToolProgress
afterExpertChatComplete
```

不能迁入通用 Renderer Chat。

## 6. File Platform 迁移

源 Chat 的 `SessionFilesPanel` 不是普通附件列表，它按以下类型组织文件：

```text
Attachments
Context
Agent Output
Search Results
```

并支持：

* Session 文件检索
* 加入和移出上下文
* 文件预览
* Agent 输出识别
* 文件关联关系

完整迁移需要同时迁移：

```text
src/renderer/src/components/files/**
src/renderer/src/hooks/files/**
src/shared/files/**
src/preload/files-api.ts
src/main/files/**
src/main/session-attachment-store.ts
src/main/attachment-staging.ts
src/main/session-context-folder-store.ts
src/main/session-model-override-store.ts
```

源 File Platform 的 Shared 层本身已经按纯契约包设计，不依赖 Electron、React 和 Node，适合整体迁移。

Preload 只负责 IPC 包装，已经有清晰的 `HermesFilesAPI` 边界。

迁移到目标后建议暴露为：

```ts
window.chatFiles
```

而不是继续扩展已经非常庞大的：

```ts
window.hermesAPI.files
```

## 7. Web Preview 处理

不迁移源项目的 `WebPreviewPanel`。

源 Chat 会通过：

```text
web-preview:navigate
```

在 Chat 内打开 WebView；目标项目已经使用：

```text
WebOperator
ShellViewManager
WebContentsView
window.aiosBrowser
```

迁移后改为：

```ts
chatNavigationPort.openWeb(url)
```

AI-OS Adapter 实现：

```text
调用 window.aiosBrowser.open(url)
→ 激活 web-operator Workspace Tab
```

这样可以避免同时存在：

```text
Chat WebView
+
WebOperator WebContentsView
```

两套浏览器会话、登录态、安全策略和审计体系。
