# 一、当前源码仍存在的关键问题

## 1. Interaction 在续跑完成前被提前标记为 Resolved

`startStreamingContinuation()` 启动异步 `sendMessage()` 后立即返回 `ChatTransportHandle`，并不等待后续 Agent 执行完成。

但 Command Handler 执行：

```ts
await continuationAdapter.continueClarify(...)
```

拿到 Handle 后立即：

```text
更新 interaction 为 resolved
发送 clarify.resolved
发送 interaction.resolved
```

真正的 Continuation Stream 此时可能才刚开始。

因此当前状态顺序实际可能是：

```text
interaction.accepted
interaction.continuing
interaction.resolved
message.delta
tool.event
completed
```

正确顺序应是：

```text
interaction.accepted
interaction.continuing
message.delta / tool.event
interaction.resolved
completed
```

---

## 2. Native Interaction API 与 Fallback 可能重复执行

当 Capability 返回：

```text
clarify_response = true
```

当前代码会：

1. 调用 `/v1/interactions/clarify`；
2. 随后仍构造 `[[hermes.clarify.response]]`；
3. 再通过 `sendMessage()` 提交一次 Session Continuation。

Approval 也存在同样逻辑。

这可能造成：

* Clarify 回答执行两次；
* Tool 被重复批准；
* 两个 Agent Response；
* 重复 Tool Call；
* Token 重复计费。

Native 与 Fallback 必须互斥。

---

## 3. Capability 探测采用过于乐观的默认值

当 `/v1/capabilities`：

* 不存在；
* 返回非 2xx；
* 网络异常；

当前默认：

```ts
session_continuation: true
```

这会把“未知能力”误判为“支持能力”。

正确规则应是：

```text
未探测成功 = unknown
unknown 不等于 supported
```

---

## 4. Continuation 没有完整继承原 Turn 上下文

初始 Chat 请求包含：

* Profile；
* Session；
* History；
* Attachments；
* Model；
* Expert；
* Team；
* Expert Run；
* Work Mode；
* Invocation Source。

但 Continuation 当前只传递：

* Profile；
* Session；
* Model；
* 一条结构化 Follow-up Message。

没有恢复：

* History；
* Attachments；
* Expert；
* Team；
* Expert Run；
* Skill；
* Work Mode；
* Permission；
* Invocation Source；
* Expert Bridge。

因此 Approval 后的续跑可能不再属于原 Expert Run，也不会继续写入原 Expert Timeline。

---

## 5. Durable Event Sequence 实际仍然是内存序列

`chat-event-sequencer.ts` 使用：

```ts
const turnSequences = new Map()
```

新进程启动后同一个 Turn 的 Sequence 会重新从 `1` 开始。

虽然 SQLite 已保存：

```text
turn.last_sequence
runtime_event.sequence
```

但 Sequencer 没有从数据库恢复起始值。

结果：

```text
重启前最后 sequence = 25
重启后 continuation sequence = 1
```

Renderer 会把新事件识别为旧事件并丢弃。

---

## 6. Runtime Store 使用的是“当前活动 Profile”的数据库

`chat-runtime-store.ts` 调用：

```ts
getDbConnection(false)
```

而 `getDbConnection()` 打开的是：

```ts
activeStateDbPath()
```

即当前活动 Profile 的 `state.db`，接口没有接收 `profileId`。

这会影响后台多 Profile Run：

```text
Run A：profile-a
Run B：profile-b
用户切换到 profile-b
Run A 后续 Event 可能写入 profile-b state.db
```

表中虽然有 `profile_id`，但数据库路由本身并未按 Profile 隔离。

---

## 7. Recovery Hook 已创建，但没有接入生产 Chat

项目新增了：

```text
useChatRuntimeRecovery
```

它能够调用 `recover()` 和 `getState()`。

但当前 `ChatSurface` 仍直接调用 `useChatController()`，没有挂载 Recovery Hook，也没有把恢复结果交给 Reducer。

因此 Renderer Reload 后：

* Pending Approval 不会重新显示；
* Queue 不会恢复；
* Turn Ledger 不会恢复；
* Last Sequence 不会恢复；
* Runtime Status 不会恢复。

---

## 8. getState 返回的数据不足以重建 Chat UI

当前 `ChatRuntimeGetStateResult` 只包含：

```text
run
turns
queue
usage
```

没有：

* Runtime Events；
* Partial Assistant Message；
* Tool Events；
* Reasoning；
* Clarify/Approval View Item；
* Last Applied Sequence；
* Message ID 映射。

Main 的 `get-state` 也没有返回 `chat_runtime_event`。

即使挂载 Recovery Hook，也无法完整恢复页面。

---

## 9. Queue 持久化目前只有数据库表，没有生产接线

Main Store 已提供：

* `upsertQueueEntry`
* `listQueueEntries`
* `deleteQueueEntry`

但 Renderer Queue 仍然是本地 `useReducer`，没有调用 Main Queue Store。

Preload Runtime API 也没有 Queue 增删改排序的 IPC。

因此当前：

```text
chat_queue_entry 表存在
≠ Queue 已持久化
```

---

## 10. Queue 高级能力没有接入 UI

Controller 已暴露：

* `removeQueued`
* `moveQueued`
* `setQueueAutoDrain`

但 `ChatSurface` 只把 Queue 转换成：

```ts
{
  text,
  attachmentsCount
}
```

交给 Composer。

当前页面没有真正提供：

* 删除；
* 修改；
* 排序；
* 暂停；
* 立即执行；
* 失败重试。

---

## 11. Turn-specific Retry 没有接入消息组件

Controller 已提供：

* `retryTurn(turnId)`
* `editAndRetryTurn(turnId)`
* `retryTurnWithCurrentContext(turnId)`

但 `ChatSurface` 仍然向所有 Error Card 传递：

```ts
retryLastTurn()
editAndRetryLastTurn()
retryLastTurnWithCurrentContext()
```

所以多个失败 Turn 中，点击早期 Error Card，仍可能重试最后一次 Turn。

---

## 12. ChatRunContextPort 没有实际传入 Controller

`ChatRunContextPort` 已定义用于恢复：

* Expert；
* Team；
* Skill；
* Work Mode；
* Permission；
* Prompt Hint；
* Model。

但 `ChatSurface` 没有 `runContext` Prop，也没有传给 `useChatController()`。

因此 Edit and Retry 仍无法恢复完整 Work Context。

---

## 13. Diagnostics 组件存在，但没有生产入口

`ChatDiagnosticsExportButton` 已实现 JSON 导出。

但当前 ChatSurface、Header 和 Settings 没有挂载该组件。

同时 Main 导出的：

```ts
fileIds: []
```

仍是固定空数组。

---

## 14. Durable Store 缺少事务与唯一序列约束

当前：

```text
append event
update run
update turn
update interaction
```

是多个独立 SQLite 操作。

数据库没有：

```sql
UNIQUE(run_id, turn_id, sequence)
```

只对 `event_id` 设置了主键。

崩溃可能产生：

* Event 已写，Turn Sequence 未更新；
* Interaction 已 resolved，Turn 仍 waiting；
* 同一 Turn 出现重复 Sequence；
* Queue Position 重复。

---

## 15. 测试仍未验证真实功能链路

Interaction Continuation 测试实际上只验证：

```text
HermesChatCommandUnsupportedError.code
```

没有调用 Continuation Adapter，也没有模拟 Gateway。

Start 测试主要验证类型结构与内存 Sequencer。

`package.json` 仍没有 Playwright、Electron E2E 或 Screenshot 命令。

# 4. FR-01 Interaction 状态机修正

## 4.1 Interaction 状态

```ts
type InteractionStatus =
  | "pending"
  | "accepted"
  | "continuing"
  | "resolved"
  | "failed";
```

合法流转：

```text
pending
→ accepted
→ continuing
→ resolved

pending
→ accepted
→ failed

continuing
→ failed
```

禁止：

```text
continuing
→ resolved
→ message.delta
```

---

## 4.2 Continuation Adapter 返回 Completion

替换：

```ts
Promise<ChatTransportHandle>
```

为：

```ts
type ChatContinuationExecution = {
  handle: ChatTransportHandle;
  completion: Promise<ChatContinuationResult>;
};

type ChatContinuationResult =
  | {
      ok: true;
      sessionId: string;
      response: string;
      usage?: ChatUsage;
    }
  | {
      ok: false;
      code: string;
      error: string;
    };
```

Command Handler：

```text
await adapter.start()
→ emit interaction.continuing
→ await execution.completion
→ 更新 resolved
→ emit interaction.resolved
```

---

## 4.3 Native 与 Fallback 互斥

执行规则：

```text
native capability supported
→ 只调用 Native API
→ 订阅 Native Continuation Stream

native unsupported
+ session continuation supported
→ 只执行 Structured Streaming Fallback

均不支持
→ GATEWAY_UNSUPPORTED
```

禁止同一 Command 同时调用两条路径。

---

## 4.4 Capability 三态

```ts
type CapabilityState =
  | "supported"
  | "unsupported"
  | "unknown";
```

探测失败时：

```text
unknown
```

不得默认 `session_continuation = true`。

增加 Capability Cache：

```text
profileId
gatewayVersion
capabilities
expiresAt
lastError
```

# 17. 核心 E2E 场景

## E2E-01 Native Clarify

```text
clarify.requested
→ 用户回答
→ Native API 调用一次
→ 不调用 Fallback
→ Continuation Stream
→ interaction.resolved
→ completed
```

## E2E-02 Fallback Clarify

```text
Native unsupported
→ Streaming Fallback 调用一次
→ 使用原 Session/Profile/Model/Expert
→ 后续 Response 回流
```

## E2E-03 Approval Restart

```text
出现 Approval
→ 关闭应用
→ 重新启动
→ Approval Card 恢复
→ Approve
→ Tool 继续执行
```

## E2E-04 Durable Sequence

```text
Turn sequence 1–15
→ Main Restart
→ Continuation
→ 下一 Event sequence = 16
```

## E2E-05 Multi-profile

```text
Profile A Run
Profile B Run
→ 同时执行
→ 分别写入各自 state.db
→ 切换 Profile 不串数据
```

## E2E-06 Queue Recovery

```text
排队 B、C
→ 关闭应用
→ 重启
→ B、C 顺序恢复
→ B、C 正常执行
```

## E2E-07 Turn Retry

```text
Turn A 失败
Turn B 失败
→ 点击 A Retry
→ 只重试 A
→ 不重复 A User Message
```

# 21. 验收标准

## Interaction

* Native 与 Fallback 不会重复执行；
* Resolved 只在 Continuation 完成后发送；
* Continuation 保留完整 Work Context；
* 嵌套 Clarify/Approval 可继续处理；
* 不支持时明确返回错误。

## Durable Runtime

* Sequence 跨重启连续；
* Event 不重复应用；
* Store 操作具有事务性；
* 多 Profile 使用独立数据库；
* Runtime Reload 可重建页面。

## Queue

* Queue 真正写入 Main Store；
* 可排序、删除、暂停和立即执行；
* 附件与上下文不丢失；
* 应用重启后恢复。

## Retry

* Retry 与具体 Turn 绑定；
* 不重复 User Message；
* Edit and Retry 恢复完整上下文；
* Retry with Current Context 使用当前配置。
