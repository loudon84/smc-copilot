# 源码复核结论

本次复核基于最新提交：

```text
d51e4035e66f5171bdd0c1903f4f7324b0cc4c46
PRD v8.0.4 : chat turn lifecycle
```

v8.0.4 已完成首轮 Session 竞态、Composer 清空、`turnId` 隔离和右侧浮动栏。提交计划同时明确：**Playwright Electron E2E 与截图基线仍未实施，继续顺延**。

下一版本不应继续调整基础布局，应处理目前剩余的三个生产闭环：

1. Clarify / Approval 只是 UI，Main Process 实际没有执行；
2. Queue、Retry、附件和文件计数仍存在数据丢失或占位实现；
3. 缺少真实 Electron E2E，现有测试不能证明跨进程和页面行为正确。

---

## 1. 当前源码仍存在的问题

### 1.1 Clarify 与 Approval 命令是空实现

Renderer 已经可以发出：

```text
clarify.respond
approval.approve
approval.deny
```

但 Main Process 的 `chat-runtime:command` 仅验证参数、读取 Active Run，然后直接返回：

```ts
return { ok: true }
```

没有把用户选择传给 Hermes Gateway，也没有改变 Run 状态。

这意味着：

* 点击 Approve 后工具不会继续；
* 点击 Deny 后工具不会真正终止；
* 回答 Clarify 后 Agent 不会收到答案；
* UI 可能显示操作完成，但后端仍停在等待状态。

---

### 1.2 Command 没有 `turnId`

当前 Chat Runtime Event 已经使用：

```text
runId + turnId
```

隔离每一轮执行。

但 `ChatRuntimeCommand` 仍只有：

```ts
runId
requestId
```

没有 `turnId`、`sessionId` 或期望状态。

如果旧 Approval Card、迟到事件或上一轮请求仍存在，Command 可能被错误提交到当前轮。

---

### 1.3 Main Active Run 无法处理交互命令

`ChatRunHandle` 当前只保存：

```ts
abort
profileId
sessionId
startedAt
```

没有保存：

* `turnId`；
* `respondClarify`；
* `approveRequest`；
* `denyRequest`；
* Pending Request；
* Runtime continuation handle。

因此 Main 即使收到 Command，也没有可调用的执行对象。

---

### 1.4 Session Files 数量仍然硬编码为 0

右侧浮动栏已经支持文件数量 Badge，但 Host 实际传入：

```tsx
sessionFilesCount={0}
```

因此：

* 上传文件后 Badge 不更新；
* Agent Output 出现后 Badge 不更新；
* Context 文件增删后 Badge 不更新；
* 用户无法从浮动按钮判断当前会话文件数量。

---

### 1.5 Queue 只保存文本，不保存附件和上下文

`useChatQueue` 当前结构只有：

```ts
id
text
enqueuedAt
```

当用户在 Agent 正在执行时提交带附件的下一条消息：

1. Composer 被清空；
2. 文本进入 Queue；
3. 附件状态被清除；
4. Queue 重放时只有文本。

这会导致附件静默丢失。

---

### 1.6 Retry 只重试文本

当前 Error Message 向前查找最近一条 User Message，然后只把文本交给：

```text
Retry
Edit and retry
```

没有恢复原轮次的：

* 附件；
* Model；
* Expert；
* Skill；
* Permission；
* Work Mode；
* Prompt Hint；
* Context Folder。

因此 Retry 不是原请求的幂等重放。

---

### 1.7 浮动栏测试没有验证真实布局

当前 Floating Actions 测试只验证：

```text
Prompt 数量少于 2 时隐藏
Prompt 数量达到 2 时显示
```

没有渲染 `ChatFloatingRail`，也没有验证 DOM 层级、坐标、滚动或右侧面板联动。

---

### 1.8 没有 Electron E2E 测试框架

`package.json` 仍只有 Vitest，没有：

* Playwright；
* Electron launcher；
* `test:e2e:electron`；
* Screenshot Regression；
* CI E2E Gate。

当前提交本身也明确将 Electron E2E 顺延。

---

### 1.9 仍保留迁移期双 API

当前代码仍保留：

* `forcedSessionId`；
* `send(text?)`；
* `filesToggleSlot`。

这些已经标记为 deprecated，但仍位于生产接口中。

继续保留会让后续调用重新走回旧语义。

# 4. Chat Runtime Command 协议

## 4.1 Command 必须携带 Turn 信息

修改为：

```ts
export type ChatRuntimeCommandBase = {
  runId: string;
  turnId: string;
  requestId: string;
  sessionId?: string;
};

export type ChatRuntimeCommand =
  | ChatRuntimeCommandBase & {
      type: "clarify.respond";
      answer: string;
    }
  | ChatRuntimeCommandBase & {
      type: "approval.approve";
    }
  | ChatRuntimeCommandBase & {
      type: "approval.deny";
      reason?: string;
    };
```

Main 必须校验：

```text
Run 存在
Turn 匹配
Request 存在
Request 类型匹配
Request 尚未处理
Run 正处于对应 waiting 状态
```

---

## 4.2 Command Result 扩展

```ts
export type ChatRuntimeCommandResult =
  | {
      ok: true;
      runId: string;
      turnId: string;
      requestId: string;
      acceptedAt: number;
    }
  | {
      ok: false;
      code:
        | "RUN_NOT_FOUND"
        | "TURN_MISMATCH"
        | "REQUEST_NOT_FOUND"
        | "REQUEST_ALREADY_RESOLVED"
        | "INVALID_STATE"
        | "GATEWAY_UNSUPPORTED"
        | "COMMAND_FAILED";
      error: string;
    };
```

禁止继续无条件返回 `ok: true`。

# 5. Main Process 交互注册表

## 5.1 扩展 ChatRunHandle

```ts
export type PendingInteraction =
  | {
      type: "clarify";
      requestId: string;
      turnId: string;
      createdAt: number;
    }
  | {
      type: "approval";
      requestId: string;
      turnId: string;
      toolName: string;
      createdAt: number;
    };

export type ChatRunHandle = {
  runId: string;
  turnId: string;
  profileId: string;
  sessionId?: string;
  startedAt: number;

  abort(): void;

  respondClarify?(
    requestId: string,
    answer: string,
  ): Promise<void>;

  approve?(
    requestId: string,
  ): Promise<void>;

  deny?(
    requestId: string,
    reason?: string,
  ): Promise<void>;

  pendingInteractions: Map<string, PendingInteraction>;
};
```

---

## 5.2 Pending Interaction 生命周期

```text
Gateway emits clarify.requested
→ Main registers PendingInteraction
→ Renderer shows Card
→ User submits Command
→ Main validates run/turn/request
→ Main forwards to Hermes
→ Hermes acknowledges
→ Main emits *.resolved
→ PendingInteraction removed
→ Run returns to streaming
```

失败时：

```text
Command failed
→ interaction.failed
→ Card remains actionable
→ Run remains waiting
```

---

## 5.3 Hermes Command Adapter

新增：

```text
src/main/chat-runtime/
  hermes-chat-command-adapter.ts
```

接口：

```ts
export interface HermesChatCommandAdapter {
  respondClarify(input: {
    profileId: string;
    sessionId?: string;
    requestId: string;
    answer: string;
  }): Promise<void>;

  approve(input: {
    profileId: string;
    sessionId?: string;
    requestId: string;
  }): Promise<void>;

  deny(input: {
    profileId: string;
    sessionId?: string;
    requestId: string;
    reason?: string;
  }): Promise<void>;
}
```

实施时按以下优先级：

1. Hermes Gateway 原生 Command API；
2. Hermes SSE continuation endpoint；
3. 结构化 Follow-up Message Adapter；
4. Gateway 不支持时返回 `GATEWAY_UNSUPPORTED`。

禁止继续“接受命令但不执行”。

## 7.3 Retry 规则

### Retry

直接重放原 `ChatTurnRequestSnapshot`。

### Edit and retry

恢复：

* 原文本；
* 原附件；
* 原 Model；
* 原 Work Context；

但不自动发送。

### Retry with current context

使用原文本和附件，但使用当前：

* Model；
* Expert；
* Skill；
* Permission；
* Work Mode。

三个动作应明确区分。

# 8. 附件事务修复

当前附件测试只验证最终附件状态为空，没有验证附件是否真实进入 Runtime Submit。

必须调整提交方法：

```ts
async function submitSnapshot(
  snapshot: ChatTurnRequestSnapshot,
): Promise<void> {
  await runtime.submit({
    ...
    attachments: snapshot.attachments.map(...)
  });
}
```

不得在 `submitMessage()` 中重新读取可变的：

```text
stateRef.current.attachments
```

验收：

```text
上传文件
→ 正在执行时提交到 Queue
→ 原附件进入 Queued Snapshot
→ Queue 重放
→ Runtime Submit 附件 ID 完整一致
```

# 12. 关键 E2E 场景

## E2E-01 Clarify

```text
发送 Prompt
→ Gateway 返回 clarify.requested
→ Card 显示
→ 输入回答
→ Main 转发
→ Gateway 继续输出
→ Card resolved
→ Turn completed
```

## E2E-02 Approval

```text
Tool 请求审批
→ Approve
→ Gateway 收到 approval
→ Tool 执行
→ Tool Result 显示
→ Turn completed
```

## E2E-03 Deny

```text
Tool 请求审批
→ Deny + 原因
→ Gateway 收到 deny
→ Tool 不执行
→ Agent 返回替代方案
```

## E2E-04 Queue Attachment

```text
Turn A streaming
→ 输入 Turn B + PDF
→ Turn B 进入 Queue
→ Turn A completed
→ Turn B 自动提交
→ Runtime 收到 PDF attachment_id
```

## E2E-05 Retry Snapshot

```text
Turn failed
→ 切换 Model
→ 点击 Retry
→ 仍使用原 Turn Model
→ 点击 Retry with current context
→ 使用新 Model
```

## E2E-06 File Badge

```text
Session Files Badge = 0
→ 上传 2 个文件
→ Badge = 2
→ Agent Output 新增
→ Badge = 3
→ 删除一个
→ Badge = 2
```

# 16. 验收标准

## Human-in-the-loop

* Clarify 回答真实传入 Hermes；
* Approval 真实控制 Tool；
* Deny 真实阻止 Tool；
* Command 按 runId、turnId、requestId 校验；
* 重复提交被拒绝；
* 失败可以重试。
