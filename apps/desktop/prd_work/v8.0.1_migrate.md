# ai-os-desktop Chat v8.0 源码复核与下一阶段迁移合并任务

## 1. 源码复核结论

当前最新提交为：

```text
commit: 8cf54fdca15412f1baa9a923f4814dbd296a8df8
message: PRD v8.0 针对 hermes-desktop/chat 模块迁移合并到 smc-copilot
```

该提交已经建立以下基础：

# 3. 当前最严重的问题

## 3.1 新 Chat 实际上不具备多轮会话能力

这是当前最高优先级缺陷。

`ChatSurface` 内部虽然维护本地 `messages`，但发送时只执行：

```ts
await submit(text)
```

没有传递当前历史消息。

而 `useChatActions` 的默认参数为：

```ts
history = []
```

因此所有请求提交给 Hermes 时，`history` 基本为空。

同时，Main 返回的 `session.started` 事件没有在 `ChatSurface` 中处理，新的 Hermes Session ID 没有保存到组件状态，也没有写回 `HermesWorkspaceContext`。

结果是：

1. 第一条消息创建一个 Hermes Session；
2. Renderer 忽略返回的 Session ID；
3. 第二条消息仍然没有 `resumeSessionId`；
4. 第二条消息再次创建新 Session；
5. 本地页面看起来是多轮对话，Hermes 后端实际是多个独立会话。

因此当前 `copilot` 引擎不应视为可用的正式 Chat。

## 3.7 Session Reconciler 当前没有任何实际效果

`chat-session-reconciler.ts` 可以定时读取 Session DB。

但是注册时传入的是空回调：

```ts
startSessionReconcile(runId, input.sessionId, () => {
  /* Renderer polls via session port; Main keeps DB warm */
})
```

读取结果：

* 没有发送给 Renderer；
* 没有转换成 Reasoning Event；
* 没有转换成 Tool Event；
* 没有进行消息去重；
* 没有处理新创建的 Session；
* 仅在提交前已经存在 `input.sessionId` 时启动。

当前 Reconciler 实质上是一个无输出的数据库轮询。

## 3.8 Abort 存在未完成 Promise 风险

Main 的 `chat-runtime:submit` 返回一个等待 `onDone` 或 `onError` 的 Promise。

中止时只执行：

```ts
handle.abort()
emit cancelled
```

没有调用 `resolveChat` 或 `finishFail`。

底层 HTTP Abort 又直接忽略 `AbortError`：

```ts
if (err.name === "AbortError") return
```

这可能导致：

* Renderer 的 `ipcRenderer.invoke(chat-runtime:submit)` 永远 Pending；
* 闭包中的窗口、事件发送器和消息缓存不能及时释放；
* 多次 Stop 后产生未完成调用；
* 后续同一 Chat 再发送时存在状态污染风险。

必须增加明确的 `finishCancelled()`，保证每一个 Submit 都只完成一次。

## 3.9 Work / Expert / Team 参数连接错误

当前 `AiosCopilotChatHost` 传递的是：

```tsx
expertId={workContext.selectedExpert?.slug}
teamId={workspace.activeTeamId}
workMode={workContext.permissionMode}
```

并且没有传入：

```text
expertRunId
invocationSource
```

这里存在三个语义错误。

### Expert ID 来源错误

`WorkChatSelectedExpert` 同时包含：

```ts
expertId
slug
```

Main 的 Expert Policy 和 Runtime DB 使用的是 `expertId`，不应传 `slug`。

### workMode 字段错误

Workspace 的工作模式是：

```ts
"ask" | "plan" | "craft"
```

而 `permissionMode` 是：

```ts
"default" | "ask_each_time"
```

当前把权限模式写入了工作模式字段。

### Expert Run 丢失

Legacy 代码正确传递：

```ts
expert_id: ws.activeExpertId
team_id: ws.activeTeamId
expert_run_id: ws.activeRunId
work_mode: ws.workMode
invocation_source: workspace mode
```

新 Host 没有传递 `workspace.activeRunId`，所以：

* Expert Run 事件无法记录；
* Team 首次消息无法触发 dispatch；
* Tool Progress 无法写入 Expert Run Timeline；
* Agent Response 无法创建 Expert Artifact；
* Run 完成状态无法更新。

# 5. P0：恢复基本可用性

## 5.1 临时将默认引擎恢复为 Legacy

在以下问题修复前：

* 多轮会话；
* Session ID；
* History；
* Abort Promise；
* Expert Run 参数；

默认引擎建议改为：

```ts
const engine =
  import.meta.env.VITE_CHAT_ENGINE || "legacy"
```

Copilot 引擎继续通过显式配置启用：

```env
VITE_CHAT_ENGINE=copilot
```

这不是回退迁移，而是避免未闭环的新入口直接替换稳定入口。

## 5.2 建立 Chat Controller

新增：

```text
src/renderer/src/modules/chat/controller/
  useChatController.ts
  chatReducer.ts
  chatHistoryMapper.ts
  chatRuntimeEventReducer.ts
```

Controller 必须管理：

* `activeSessionId`
* `activeRunId`
* `messages`
* `streamingMessage`
* `reasoning`
* `toolEvents`
* `usage`
* `attachments`
* `selectedModel`
* `queue`
* `runState`
* `lastError`

不得继续把这些状态零散放在占位 `ChatSurface` 内。

## 5.3 完成 Session 生命周期

必须实现：

```text
forcedSessionId
    ↓
load session history
    ↓
submit message
    ↓
session.started
    ↓
保存 activeSessionId
    ↓
写回 HermesWorkspaceContext
    ↓
后续请求使用 resumeSessionId
```

同时：

* 每次发送传递当前 History；
* Session 创建后迁移 Draft Attachments；
* 新 Session 写入 Session Cache；
* New Chat 清理 Session、Model Override 和文件状态；
* Session 切换时停止旧 Session 的 UI 事件更新。

## 5.4 修复 Abort 生命周期

Main 中每个 Run 必须具有统一完成函数：

```ts
finishCompleted()
finishFailed()
finishCancelled()
```

要求：

* 三个函数互斥，只能执行一次；
* Abort 必须完成 `ipcRenderer.invoke` 对应 Promise；
* Abort 必须停止 Reconciler；
* Abort 必须清理 Active Run；
* Abort 必须保留或标记部分生成内容；
* Abort 期间再次发送不能受到旧事件影响。

## 5.5 修复 Work 参数映射

新 Host 应改为：

```tsx
expertId={workspace.activeExpertId}
teamId={workspace.activeTeamId}
expertRunId={workspace.activeRunId}
workMode={workspace.workMode}
invocationSource={
  workspace.mode === "expert"
    ? "expert_chat"
    : workspace.mode === "team"
      ? "team_chat"
      : "default_chat"
}
```

权限模式应新增独立字段，例如：

```ts
permissionMode?: "default" | "ask_each_time"
```

禁止继续复用 `workMode`。

4. 清除不属于 AI-OS 的 Setup、Follow、Config UI；
5. 由新的 Controller 管理状态；
6. `source/` 最终只作为上游快照，不能作为生产入口。

目标目录建议：

## 6.3 统一消息模型

* `UiMessage`

下一阶段必须定义一个 Renderer Canonical Model，例如：

```ts
type ChatViewItem =
```

禁止继续依赖 `role: string`、`kind?: string` 进行模糊判断。

# 10. P2：多会话与后台运行迁移

copilot-desktop 的原设计是：

```text
一个 ChatRun 对应一个挂载中的 Chat
多个 ChatRun 可以同时存在
只有当前 Chat 可见
后台 Chat 继续流式执行
```

ai-os-desktop 当前只挂载单个 Chat 页面。

下一阶段应新增：

```text
ChatWorkspaceManager
  ├── ChatRunRegistry
  ├── ActiveRun
  ├── runId ↔ sessionId
  ├── runId ↔ profileId
  ├── runId ↔ expertRunId
  ├── title
  ├── loading
  └── unread/completed state
```

要求：

* 三个 Chat 可以同时生成；
* 每个 Chat 事件只进入自己的 Controller；
* 切换页面不会停止后台生成；
* Abort 只停止当前 Chat；
* Session 创建后更新对应 Run；
* Expert 与 Team Chat 不串流；
* 完成后可显示后台完成通知。

```bash
npm ci
```

## 最终判断

PRD v8.0 不应定义为“Chat 模块迁移完成”，更准确的状态是：

```text
Chat Migration Foundation Completed
Chat Runtime / UI / File Integration Pending
```

下一步最重要的不是继续复制更多源码，而是完成以下三个闭环：

1. **Session 与 Runtime 闭环**；
2. **迁入 Chat UI 的生产接管**；
3. **File Platform 从 `_upstream` 转为正式服务**。

其中第一优先级是修复 Session ID、History 和 Abort。只有这三个问题关闭后，新的 Copilot Chat 才具备继续合并其他功能的基础。
