# Hermes Desktop 文件管理与富内容组件克隆 RPD

版本：v1.0
目标项目：`fathah/hermes-desktop`
参考项目：`chatboxai/chatbox`
基线日期：2026-07-21
实施原则：能力复刻、独立实现、保持 Hermes 架构兼容

---

## 1. 项目目标

在不改变 Hermes Agent 核心运行时、不重构现有 Chat 主流程的前提下，将 Chatbox 中成熟的文件管理和内容组件抽象方式重新实现到 Hermes Desktop。

最终形成四个稳定能力层：

```text
Hermes File Platform
├─ File Domain
│  ├─ 文件选择、拖入、粘贴
│  ├─ 文件暂存与持久化
│  ├─ 文件解析与状态管理
│  └─ 文件与 Session/Message 关联
│
├─ File UI Components
│  ├─ Composer 附件托盘
│  ├─ 消息附件网格
│  ├─ 文件卡片与右键菜单
│  ├─ 文件预览面板
│  └─ 文件操作状态卡片
│
├─ Rich Content Components
│  ├─ Markdown
│  ├─ Code Block
│  ├─ Mermaid
│  ├─ SVG
│  ├─ Image
│  └─ HTML Artifact
│
└─ File Context Adapter
   ├─ 全文上下文注入
   ├─ 大文件分段
   ├─ 会话级文件检索
   └─ Hermes Attachment 兼容转换
```

本项目不是将 Chatbox 整体移植到 Hermes Desktop，也不包含：

* 模型管理克隆
* Chatbox 会话存储克隆
* Chatbox 云服务
* Chatbox 联网搜索
* Chatbox UI 主题完整复制
* Chatbox 商业功能
* 独立企业知识库平台
* 替换 Hermes Agent 的文件工具

Chatbox 已将输入附件、消息附件、Markdown、Mermaid、Artifact、文件解析和会话附件检索拆分为独立目录或组件。

说明 Chatbox 没有把附件、Markdown、消息、文件预览全部堆在一个 Chat 组件中，而是按输入、消息展示、内容类型和文件处理进行解耦。

本项目复刻的是上述**职责划分和产品能力**，而不是直接复制源文件。

## 3. Hermes Desktop 当前基线

Hermes Desktop 当前已经具有可继续演进的附件基础。

现有共享附件模型定义了：

```ts
type AttachmentKind =
  | "image"
  | "text-file"
  | "path-ref";
```

附件数据已经能够表达：

* 图片 Data URL
* UTF-8 文本内容
* PDF、DOCX 等本地文件路径
* 原始文件大小
* 压缩后文件大小
* MIME
* 文件名

Main Process 已存在：

```text
attachment-staging.ts
session-attachment-store.ts
media.ts
```

其中 `attachment-staging.ts` 会为没有原始路径的粘贴附件创建本地文件，并按 Session 保存；当前实现还对 Session ID 和文件名进行了路径字符过滤和唯一文件名处理。

当前 Session 附件持久化主要针对图片，在 SQLite 中按 `message_id + session_id + ordinal` 保存附件数据，并可在会话恢复时重新装载。

Renderer 已有：

```text
AgentMarkdown.tsx
AttachmentChip.tsx
MediaImage.tsx
```

现有 `AttachmentChip` 支持图片预览、保存、移除和文件大小提示；`AgentMarkdown` 已提供 GFM、代码高亮、Diff、代码复制及流式代码块状态处理。

因此，本项目不重新设计附件上传底层，而是：

1. 扩展现有 `Attachment` 为完整文件领域模型。
2. 将图片专用持久化升级为通用文件关联。
3. 将现有零散组件收敛成稳定组件包。
4. 在现有 Hermes IPC 安全边界上新增文件 API。

Hermes Desktop 的 Renderer 不应直接访问 Node.js 或文件系统；所有能力必须经过 Renderer → Preload → Main Process，并保持 Profile 隔离。

## 8. 兼容现有 Attachment 模型

短期内不能删除现有：

```ts
Attachment
```

新增适配器：

```ts
export interface AttachmentAdapter {
  toManagedFile(
    attachment: Attachment,
    context: AttachmentContext,
  ): Promise<ManagedFile>;

  toHermesAttachment(
    file: ManagedFile,
    parsed?: ParsedDocument,
  ): Promise<Attachment>;
}
```

兼容规则：

| ManagedFile    | 现有 Attachment        |
| -------------- | -------------------- |
| 图片             | `kind: "image"`      |
| 小型纯文本          | `kind: "text-file"`  |
| PDF、Office、大文件 | `kind: "path-ref"`   |
| 粘贴文件           | 先持久化，再使用 `path-ref`  |
| Agent 输出文件     | 使用 `path-ref`        |
| 文件检索片段         | 不作为 Attachment，写入上下文 |

这样第一阶段不要求 Hermes Agent 修改接口。

## 9. 文件状态机

```text
SELECTED
   │
   ▼
STAGING
   │
   ├─失败──────────────► FAILED
   │
   ▼
STORED
   │
   ▼
PARSING
   │
   ├─不支持────────────► READY（仅文件引用）
   ├─失败──────────────► FAILED
   │
   ▼
PARSED
   │
   ├─无需索引──────────► READY
   │
   ▼
INDEXING
   │
   ├─失败──────────────► READY_WITHOUT_INDEX
   │
   ▼
READY
```

UI 不允许只展示一个永久转圈状态。

每个状态必须对应用户可见反馈：

| 状态       | UI          |
| -------- | ----------- |
| selected | 文件名、大小、移除   |
| staging  | 正在保存        |
| parsing  | 正在读取内容      |
| indexing | 正在建立会话索引    |
| ready    | 可预览、可发送     |
| failed   | 错误原因、重试、移除  |
| missing  | 原文件不存在、重新定位 |
| deleted  | 从界面隐藏       |

## 10. 文件存储布局

所有路径必须经过 Profile 根目录解析，不允许直接在业务模块中硬编码 `~/.hermes`。

建议布局：

```text
<profileHome>/
└─ desktop/
   └─ files/
      ├─ objects/
      │  └─ <sha256-prefix>/
      │     └─ <sha256>
      │
      ├─ parsed/
      │  └─ <fileId>.json
      │
      ├─ previews/
      │  └─ <fileId>/
      │
      ├─ temp/
      │
      └─ file-index.db
```

设计规则：

1. 文件以内容哈希去重。
2. `ManagedFile` 与物理文件分离。
3. 同一个文件可以关联多个 Session 和 Message。
4. 删除一个关联不立即删除物理文件。
5. 无关联文件由清理任务回收。
6. 原始文件默认不修改。
7. Picker 和 Drag Drop 文件可选择“引用原路径”或“复制到受管目录”。
8. Clipboard 文件必须写入受管目录。
9. Agent 输出文件默认引用 Workspace 文件，不重复复制。
10. Profile 之间不得共享文件索引。

## 11. SQLite 数据结构

新增表：

```sql
CREATE TABLE managed_files (
  id TEXT PRIMARY KEY,
  profile_id TEXT NOT NULL,

  name TEXT NOT NULL,
  extension TEXT NOT NULL,
  mime TEXT NOT NULL,
  category TEXT NOT NULL,

  source TEXT NOT NULL,
  status TEXT NOT NULL,

  size INTEGER NOT NULL,
  original_path TEXT,
  managed_path TEXT,
  content_hash TEXT,

  parser_id TEXT,
  parse_version INTEGER,

  error_code TEXT,
  error_message TEXT,

  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE UNIQUE INDEX idx_managed_files_profile_hash
ON managed_files(profile_id, content_hash);

CREATE TABLE file_associations (
  id TEXT PRIMARY KEY,
  file_id TEXT NOT NULL,
  profile_id TEXT NOT NULL,

  session_id TEXT,
  message_id TEXT,
  task_id TEXT,

  role TEXT NOT NULL,
  ordinal INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,

  FOREIGN KEY(file_id) REFERENCES managed_files(id)
);

CREATE INDEX idx_file_associations_session
ON file_associations(profile_id, session_id);

CREATE INDEX idx_file_associations_message
ON file_associations(profile_id, message_id);

CREATE TABLE parsed_documents (
  file_id TEXT PRIMARY KEY,
  parser_id TEXT NOT NULL,
  parser_version INTEGER NOT NULL,

  title TEXT,
  text_content TEXT NOT NULL,
  metadata_json TEXT NOT NULL,
  sections_json TEXT NOT NULL,

  truncated INTEGER NOT NULL DEFAULT 0,
  parsed_at TEXT NOT NULL,

  FOREIGN KEY(file_id) REFERENCES managed_files(id)
);

CREATE TABLE file_chunks (
  id TEXT PRIMARY KEY,
  file_id TEXT NOT NULL,
  chunk_index INTEGER NOT NULL,

  content TEXT NOT NULL,
  token_count INTEGER,
  metadata_json TEXT NOT NULL,

  FOREIGN KEY(file_id) REFERENCES managed_files(id),
  UNIQUE(file_id, chunk_index)
);
```

向量数据不强制放在第一阶段。

第一阶段可以使用：

* SQLite FTS5
* 文件名搜索
* 解析文本全文搜索
* Session 文件过滤

后续再增加 embedding provider。

## 12. Parser Registry

文件解析不能写成一个不断增长的 `if/else`。

定义：

```ts
export interface FileParser {
  id: string;
  version: number;
  priority: number;

  supports(input: FileParserInput): boolean;

  parse(
    input: FileParserInput,
    signal?: AbortSignal,
  ): Promise<ParsedDocument>;
}
```

Registry：

```ts
class FileParserRegistry {
  register(parser: FileParser): void;
  unregister(parserId: string): void;
  resolve(input: FileParserInput): FileParser;
  list(): FileParserDescriptor[];
}
```

初始解析器：

| Parser     | 文件                        |
| ---------- | ------------------------- |
| `text`     | txt、log、csv、json、yaml、xml |
| `markdown` | md、mdx                    |
| `code`     | ts、tsx、js、py、java、sql 等   |
| `office`   | docx、pptx、xlsx            |
| `pdf`      | PDF                       |
| `epub`     | EPUB                      |
| `image`    | 图片元信息，OCR 为可选             |
| `fallback` | 仅生成文件引用                   |

解析实现建议：

```text
文本 / Markdown / Code
  → Node.js 本地读取

Office / EPUB
  → officeparser 或 MarkItDown Adapter

PDF
  → MarkItDown Local Service
  → 失败时 PDF 文本基础解析
  → OCR 作为独立增强路径

图片
  → 尺寸、MIME、EXIF
  → 可选 OCR/Vision，不作为基础解析阻塞项
```

解析器必须是可替换适配器，不能让 UI 依赖具体解析库。

```text
       解析状态

       预览 | 重试 | 移除
```

状态与发送规则：

* `selected/staging`：发送按钮可配置为等待或禁止。
* `parsing`：小文件允许发送，使用路径引用。
* `failed`：仍可作为路径文件发送，但显示警告。
* `missing`：禁止发送。
* `ready`：正常发送。

## 17. RichContentRenderer

现有 `AgentMarkdown.tsx` 应逐步变为：

```ts
<RichContentRenderer
  content={message.content}
  contentType="markdown"
  streaming={message.streaming}
  sourceId={message.id}
```

内部路由：

```text
Markdown AST
├─ 普通段落
├─ 表格
├─ 引用
├─ Link
├─ Inline Code
└─ Code Fence
```

```ts
interface RichBlockRenderer {
```

映射规则：

```ts
function toHermesAttachment(file: ManagedFile): Attachment {
  if (file.category === "image") {
    return imageAttachment;
  }

  if (
    file.category === "text" &&
    file.size <= textInlineLimit
  ) {
    return {
      kind: "text-file",
      text: parsedText,
      ...
    };
  }

  return {
    kind: "path-ref",

}
```

## 23. 文件安全策略

新增：

```ts
interface FileSecurityPolicy {
  maxImportBytes: number;
  maxParseBytes: number;
  allowedExtensions: string[];
  deniedExtensions: string[];
  allowArchives: boolean;
  allowExternalOpen: boolean;
}
```

强制规则：

1. Main Process 对所有路径执行 canonicalize。
2. 检查符号链接后的真实路径。
3. 禁止 `..` 路径逃逸。
4. 粘贴文件名必须重新清洗。
5. Renderer 提交的 MIME 不可信。
6. 扩展名和 Magic Bytes 同时检查。
7. 可执行文件默认不解析、不预览。
8. HTML 不允许插入主页面。
9. SVG 必须清洗。
10. 文件内容不写入日志。
11. 错误日志只记录 fileId，不记录敏感完整路径。
12. 远程模式下不假设远程服务器能访问本地路径。
13. Profile 文件不跨 Profile 查询。
14. Session 删除只删除关联；物理文件由引用计数和清理策略决定。
15. 所有 IPC 参数用 schema 校验。

默认拒绝：

```text
.exe
.dll
.com
.bat
.cmd
.ps1
.sh
.app
.dmg
.pkg
.msi
.scr
.jar
```

这些文件可以显示为附件引用，但不解析、不执行。

## 24. Local 与 Remote 模式

Hermes Desktop 支持本地和远程后端，因此文件能力必须区分传输策略。官方项目当前本身支持本地 Gateway 和远程 API 两种工作模式。

### Local Mode

```text
本地路径
  → 直接作为 path-ref 给本地 Hermes
```

### Remote Mode

本地绝对路径对远程 Hermes 无效。

Remote Mode 必须支持以下策略之一：

```text
A. 上传到远程 Gateway 临时文件接口
B. 转成文本或 Data URL 内联
C. 禁止无法上传的大文件，并明确提示
```

本 RPD 第一阶段要求：

* 图片继续按现有传输机制。
* 小型文本直接内联。
* PDF/Office 在本地解析成文本后发送。
* 不向远程 Hermes 发送本地路径。
* 大文件超限时明确提示，不静默失败。

远程文件上传 API 可作为后续独立版本。

## 26. 性能要求

### Renderer

* 附件列表不保存大 Base64 副本。
* 图片缩略图与原图分离。
* 大文本使用虚拟滚动。
* Markdown 渲染使用 `memo`。
* 代码高亮继续懒加载。
* 文件预览关闭后释放 Object URL。
* Session 切换取消未完成预览请求。

### Main

* 文件哈希使用 Stream。
* 大文件不一次性读入内存。
* Parser 支持 AbortSignal。
* 解析任务限制并发数。
* 同一内容哈希不重复解析。
* 解析结果按 parserVersion 失效。
* 文本索引异步执行。
* 应用关闭时不等待非关键索引任务无限完成。

建议默认：

```ts
MAX_CONCURRENT_PARSE_JOBS = 2
MAX_CONCURRENT_HASH_JOBS = 3
PREVIEW_TEXT_LIMIT = 2_000_000
INLINE_IMAGE_LIMIT = 8_000_000
```

## 36. 最终架构结论

本项目不应定义为“把 Chatbox 文件功能复制进 Hermes Desktop”，而应定义为：

```text
以 Chatbox 的组件职责划分为参考，
在 Hermes Desktop 内建设独立的 File Platform。
```

核心稳定抽象是：

```text
ManagedFile
FileAssociation
FileParser
FilePreviewDescriptor
AttachmentAdapter
RichBlockRenderer
```

最终调用关系：

```text
用户选择文件
  ↓
ManagedFile
  ↓
File Storage
  ↓
Parser Registry
  ↓
Preview / Session Context
  ↓
Attachment Adapter
  ↓
Hermes Agent
```

由此实现：

* UI 与文件系统解耦
* Parser 与 UI 解耦
* 文件存储与 Session 解耦
* Rich Content 与 Message 解耦
* 本地模式与远程模式解耦
* Hermes Desktop 与 Chatbox 源码解耦

这六项解耦是本 RPD 的主要验收结果。
