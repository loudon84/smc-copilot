# SMC Copilot `apps/work` 迁移方案 PRD v1.0

## Copilot Desktop → Runtime Backend Migration

**版本**：v1.0
**目标目录**：`smc-copilot/apps/work`
**基线源码**：`loudon84/copilot-desktop` 当前 `master`
**Runtime**：`smc-copilot/services/runtime`
**版本目标**：**先稳定 Work Desktop，Runtime 第一阶段只负责 Hermes Agent 安装与运行管理，不迁移 Chat/Session/File 等成熟业务链路。**

---

# 1. 核心决策

本版本改变此前 `smc-copilot/apps/desktop` 的迁移思路。

不再执行：

```text
copilot-desktop
      ↓
拆 Chat
      ↓
重新实现 ChatSurface / Port / Adapter
      ↓
Runtime ChatRun / Turn / Worker
      ↓
Hermes
```

改为：

```text
copilot-desktop
      ↓
直接作为 apps/work 基线
      ↓
保留成熟 Chat / Session / File / Workspace
      ↓
只替换 Hermes 生命周期管理实现
      ↓
services/runtime
      ↓
Hermes Agent
```

即：

> **v1.0 迁移的是 Hermes Control Plane，不是 Hermes Desktop 产品能力。**

---

# 2. 为什么这样定义

当前 `copilot-desktop` 的 `window.hermesAPI` 已经远超过早期的“60+ API”。

按当前 `src/preload/index.ts` 实际清单统计：

```text
hermesAPI 顶层能力        ≈ 249
hermesAPI.files 子 API     21
--------------------------------
合计暴露能力             ≈ 270
```

其中包括：

* Runtime
* Chat
* Streaming
* Session
* Attachment
* File Platform
* Model
* Profile
* Config
* OAuth
* Gateway
* Dashboard
* Memory
* Soul
* Skills
* Tools
* MCP
* Cron
* Kanban
* Claw3D
* Wallet
* Registry
* Updater
* Native OS

等大量能力。当前 preload 本身就是 Renderer 与 Main 之间的完整契约。

如果第一阶段就把这些全部改成 Runtime API，相当于重新实现一套 Hermes Desktop。

因此 v1.0 明确采用：

```text
Compatibility Facade Migration
```

而不是：

```text
Full Backend Rewrite
```

# 6. 最重要的不变式

v1.0 必须遵守：

### 不变式 1

**Renderer API 契约不改。**

例如：

```ts
window.hermesAPI.sendMessage()
window.hermesAPI.listSessions()
window.hermesAPI.startGateway()
```

Renderer 不需要知道：

```text
startGateway
```

背后已经变成 Runtime。

---

### 不变式 2

不批量重写：

```text
Chat.tsx
ChatInput.tsx
MessageList.tsx
SessionFilesPanel
FilePreviewPanel
WorktreePanel
```

---

### 不变式 3

Runtime 生命周期迁移必须使用：

```text
Main Compatibility Adapter
```

不得要求 Renderer 改成：

```ts
window.runtimeAPI.xxx()
```

---

### 不变式 4

v1.0 **不删除旧 hermesAPI 方法**。

即使标记 Legacy：

```text
Renderer Contract = backward compatible
```

# 11. Chat 发送链调整

唯一允许调整的地方是 Gateway readiness。

原：

```text
send-message
   ↓
Desktop 判断 Gateway
   ↓
Desktop startGateway()
   ↓
Desktop sendMessage()
```

改：

```text
send-message
   ↓
runtimeBackend.ensureReady()
   ↓
Runtime 确保 Gateway running
   ↓
原 Desktop Hermes Chat Client
   ↓
Hermes Gateway
```

也就是说：

> **Runtime 管进程，Desktop 仍管 Interactive Chat transport。**

# 75. Definition of Done

PRD v1.0 完成必须满足：

* `apps/work` 能独立启动；
* 原 `copilot-desktop` Chat Layout 与交互保持；
* 原 Chat Streaming 行为保持；
* Attachment 不回归；
* Session Resume 不回归；
* Session Files / Preview 不回归；
* Slash / `/btw` 不回归；
* Context Folder / Worktree 不回归；
* Runtime 成为 Hermes 安装唯一入口；
* Runtime 成为 Gateway 生命周期唯一 Owner；
* Desktop 不再直接启动/停止 Gateway；
* `window.hermesAPI` Renderer Contract 不发生破坏性变化；
* Remote / SSH 不回归；
* SMC Login、Hermes Panel、JSSDK Bridge、Service Settings 可后续逐项迁入；
* 不要求 v1.0 完成 Session/File/Config 的 Runtime 化。

## 最终建议

这次不要再把 v1.0 定义成 **“Desktop Thin Client Closure”**。

应该正式定义成：

> **Work Desktop Stable Baseline + Hermes Runtime Management Separation**

也就是只先拆最确定、最必要的一刀：

```text
原 copilot-desktop

Desktop UI + Hermes Control + Hermes Chat
                  │
                  │ v1.0
                  ▼

apps/work                     services/runtime
Desktop UI + Hermes Chat      Hermes Control
```

这会把第一阶段迁移范围从当前约 **270 个 Renderer 能力面**，收缩到真正需要替换实现的 **约 16 个 Runtime/Gateway 生命周期接口**，而 Chat、附件、Session、Slash、Workspace 等已经验证成熟的链路全部不动。这个范围更适合先用 `apps/work` 做稳定性验证，再决定 v1.1 是否继续拆 Profile、Config、Backup 等管理能力。
