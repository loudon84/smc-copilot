# 源码复核结论

本次复核基于最新提交：

```text
6b264e5930289c5427f3b0d3af779deaabf366a3
PRD v8.0.3 chat workspace
```

v8.0.3 已经完成 Per-Run Workspace、统一 Header、内容中轴、Composer 收敛和多 Run 持久化。当前三个问题均能从源码中定位，不属于 Hermes Agent 模型异常。

---

## 一、三个问题的根因

### 1. 首次提交完成后返回“初始化状态”

这是一个明确的 **新 Session 绑定与历史 Session 恢复混用** 问题。

当前执行链路：

```text
New Chat
→ 第一次提交
→ Hermes 返回 session.started
→ Controller 更新 activeSessionId
→ Host 更新 run.identity.sessionId
→ ChatSurface 把新 sessionId 再次作为 forcedSessionId 传回 Controller
→ useEffect 调用 loadSession()
→ LOAD_HISTORY 把 runState 重置为 idle
```

`useChatController` 只要发现 `forcedSessionId` 变化，就会执行 `loadSession()`；而 `loadSession()` 会从数据库重新加载历史。

`LOAD_HISTORY` 在 Reducer 中会直接：

```ts
streamingMessageId: null
toolProgress: null
runState: "idle"
```

与此同时，Main Process 在 `onSessionStarted` 中发送一次 `session.started`，在 `onDone` 中又可能发送一次相同事件，然后才发送 `completed`。

因此存在以下竞态：

```text
completed
    ↓
异步 loadSession 返回
    ↓
LOAD_HISTORY
    ↓
completed 被覆盖为 idle
```

第一次提交会触发该问题，因为最初没有 Session ID；第二次提交时 `loadedSessionRef` 已经记录该 Session，所以通常可以正常返回。

---

### 2. 提交后 Input 内容没有清空

当前 `ChatSurface` 调用：

```tsx
onSend={(text) => void send(text)}
```

但 Controller 的清空逻辑是：

```ts
if (!overrideText) {
  inputRef.current = "";
  bumpInput();
}
```

当调用 `send(text)` 时，`overrideText` 有值，所以不会进入清空分支。

而 `CopilotChatInput` 提交时始终执行：

```ts
onSend(text)
```

自身也没有调用 `onChange("")`。

此外，Host 还会把输入内容持久化到：

```ts
run.presentation.draft
```

当前发送成功后没有清空 Draft，因此即使临时清空 UI，切换 Run 后旧文本仍可能重新出现。

---

### 3. 多轮对话与 Session Files 按钮没有位于最右侧浮动区域

当前多轮对话按钮对应 `PromptNavigator`。

但它被直接渲染在：

```tsx
<div className="chat-messages-scroll">
  ...
  <PromptNavigator />
</div>
```

折叠状态下的 `prompt-navigator-trigger` 只是普通 Button，没有绝对定位，所以会参与消息区正常文档流，截图中最终落到了左下方。只有展开后的 Panel 使用了 `position: absolute`。

Session Files Button 则被作为：

```tsx
filesToggle={filesToggleSlot}
```

传入 `CopilotChatInput`，最终渲染在 Composer 左侧工具栏中。

所以当前两个按钮实际上属于不同布局容器，并没有统一的右侧浮动承载层。

# 4. Session 生命周期重构

## 4.1 区分“恢复 Session”和“绑定 Session”

当前一个 `sessionId` 同时承担：

* 打开旧 Session 时恢复历史；
* 新对话执行后绑定 Hermes Session。

必须拆分为：

```ts
type ChatSurfaceProps = {
  initialSessionId?: string | null;
  boundSessionId?: string | null;
};
```

### initialSessionId

只用于：

* 打开历史会话；
* 应用重启恢复；
* 首次挂载加载消息。

特征：

* 组件挂载时固定；
* 只允许加载一次；
* 后续更新不触发历史加载。

### boundSessionId

用于：

* `session.started`；
* Runtime 返回最终 Session；
* Run Workspace 持久化；
* 后续消息 Resume。

特征：

* 只更新 Session 绑定；
* 不加载历史；
* 不修改 `runState`；
* 不清空 Streaming Message。

---

## 4.2 Controller API 调整

将：

```ts
forcedSessionId?: string | null
```

替换为：

```ts
initialSessionId?: string | null
```

Controller 内部增加：

```ts
const initialHydrationIdRef = useRef(initialSessionId);
const hydratedSessionIdRef = useRef<string | null>(null);
const runtimeBoundSessionIdRef = useRef<string | null>(null);
```

初始化加载规则：

```ts
const canHydrate =
  initialHydrationIdRef.current &&
  hydratedSessionIdRef.current == null &&
  state.runState === "idle" &&
  state.messages.length === 0;
```

禁止使用实时变化的 Workspace `sessionId` 触发 Hydration。

---

## 4.3 新增两种 Reducer Action

```ts
type ChatControllerAction =
  | {
      type: "HYDRATE_SESSION";
      sessionId: string;
      messages: ChatViewItem[];
      requestId: string;
    }
  | {
      type: "BIND_SESSION";
      sessionId: string;
      source: "runtime" | "submit_result";
    };
```

### HYDRATE_SESSION

只允许在以下状态执行：

```text
idle
interrupted
```

禁止在以下状态覆盖当前消息：

```text
creating
streaming
waiting_approval
waiting_clarify
completed
failed
cancelled
```

### BIND_SESSION

只更新：

```ts
activeSessionId
```

不得修改：

```ts
messages
streamingMessageId
toolProgress
runState
usage
```

---

## 4.4 Hydration 竞态保护

每次历史加载生成：

```ts
const hydrationRequestId = crypto.randomUUID();
```

加载完成时校验：

```ts
if (hydrationRequestId !== latestHydrationRequestId.current) return;
if (stateRef.current.runState !== "idle") return;
if (stateRef.current.messages.length > 0) return;
```

Run 切换、开始提交或组件卸载时取消旧 Hydration。

# 5. Turn 生命周期

## 5.1 增加 turnId

当前 Runtime 只通过 `runId` 隔离不同会话，但同一个 Run 内多轮请求仍共享同一个事件通道。

新增：

```ts
type ChatSubmitInput = {
  runId: string;
  turnId: string;
  ...
};
```

所有 Runtime Event 增加：

```ts
type ChatRuntimeEvent = {
  runId: string;
  turnId: string;
  ...
};
```

Controller 只消费：

```ts
event.runId === activeRunId &&
event.turnId === activeTurnId
```

迟到的上一轮事件直接丢弃。

---

## 5.2 新增 Turn State

```ts
type ChatTurnState = {
  turnId: string | null;
  turnSequence: number;
  startedAt: number | null;
  completedAt: number | null;
  terminalState:
    | "completed"
    | "failed"
    | "cancelled"
    | null;
};
```

每次发送执行：

```text
BEGIN_TURN
→ 创建 turnId
→ 清空上一轮 usage/toolProgress
→ startedAt = Date.now()
→ completedAt = null
```

当前 Workspace 的 `startedAt` 只在未设置时赋值，后续轮次会继续使用旧时间。

必须改为：

```ts
if (previousState is terminal/idle && nextState is busy) {
  startedAt = Date.now();
  completedAt = undefined;
}
```

---

## 5.3 终态单调性

为每个 Turn 定义合法状态：

```text
idle
  → creating
  → streaming
  → waiting_approval / waiting_clarify
  → streaming
  → completed / failed / cancelled
```

进入终态后，同一 `turnId` 的以下事件不得再次改变状态：

* `message.delta`
* `reasoning.delta`
* `tool.progress`
* `tool.event`
* `session.started`

只有新 `turnId` 才能开启下一轮。

---

## 5.4 Session Started 事件去重

Main Process 增加：

```ts
let emittedSessionId: string | undefined;

function emitSessionStartedOnce(sessionId: string): void {
  if (emittedSessionId === sessionId) return;
  emittedSessionId = sessionId;
  emit(...);
}
```

`onSessionStarted` 和 `onDone` 均调用该函数。

禁止在同一轮发送两次完全相同的 `session.started`。

# 6. Composer 提交事务

## 6.1 移除 send(overrideText) 模糊语义

当前：

```ts
send(text?)
```

同时承担：

* Composer 提交；
* Queue 重放；
* Suggestion 提交；
* Retry。

改为：

```ts
submitComposer(): Promise<void>;

submitPayload(
  payload: ChatComposerSubmission,
): Promise<void>;
```

数据结构：

```ts
type ChatComposerSubmission = {
  text: string;
  attachments: ChatAttachmentState[];
  source:
    | "composer"
    | "queue"
    | "retry"
    | "suggestion";
};
```

---

## 6.2 提交流程

用户点击 Send 或按 Enter 后，必须同步执行：

```text
1. Capture text
2. Capture attachments
3. setInput("")
4. setAttachments([])
5. persist Run draft = ""
6. append User Message
7. append Pending Assistant Message
8. runtime.submit()
```

Input 清空不能等待：

* Gateway 启动；
* Session 创建；
* 模型响应；
* Runtime Promise 完成。

验收要求：

```text
点击 Send 后 50ms 内 Input 为空
```

---

## 6.3 Draft 单一更新入口

Controller 增加：

```ts
onDraftChange?: (value: string) => void;
```

统一方法：

```ts
function commitInput(value: string): void {
  setInputState(value);
  onDraftChange?.(value);
}
```

以下操作全部必须调用 `commitInput`：

* 用户输入；
* Suggestion；
* Voice；
* Slash；
* Send 清空；
* New Chat；
* Run Reset；
* Draft Restore。

禁止 Host 和 Controller 分别维护两套未同步的 Composer 文本。

---

## 6.4 使用 useState 替代 inputRef + bumpInput

当前输入通过：

```ts
inputRef.current
bumpInput()
```

模拟受控状态。

改为：

```ts
const [input, setInputState] = useState("");
```

原因：

* 清空行为可预测；
* React 状态与 Textarea 一致；
* Draft Effect 可监听；
* 测试不需要依赖强制重绘计数器；
* 减少 stale closure。

---

## 6.5 失败后的恢复策略

请求失败时不自动将文本写回 Input。

消息区域保留用户消息，并提供：

```text
Retry
Edit and retry
Copy
```

`Edit and retry` 才将原文本恢复到 Composer。

# 12. 验收标准
